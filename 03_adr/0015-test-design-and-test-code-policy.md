# ADR-0015: インポート系・Web改修のテスト設計・テストコードの進め方

- 決定者・関係者: 野澤有沙、佐々木航太（UDS）
- 出典: 文字起こし 01:30:57〜01:46:00（要確認）（Geminiメモ: https://docs.google.com/document/d/1n-Av2kjhakuFZvuhaYh-807svACt8pbR069ukM9-Nd4）

## コンテキスト
- AIでテストコードを作る場合、ビジネスロジックとそれ以外の切り分けや、生成されたテストの正しさを判断しにくく、開発者に任せると品質にばらつきが出る。
- 現状、上田・小澤は野澤の設計書をそのままAIに渡して実装しており、設計書にないことは考慮されない。今回は設計書を完璧には書かない方針。
- UDS Web側には、テストコードがほぼない。

## 選択肢
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | 開発者が先にテスト設計を行い、レビューを受けてから、その通りにテストコードを作る | 品質のばらつきを抑えられる | レビューする人（野澤は入らない想定）が必要。レビューの穴が残る |
| B | 森に責任を持たせ、不具合が出たときに直す（井上のスタンスと野澤が説明） | 間に合わせやすい | 不具合が出るまで気づけない |
| C | Web側はテストコードを書かず、画面での判定にする | 現実的な工数 | 回帰テストの資産が残らない |

## 判断軸
- 開発スケジュールに間に合うか。
- レビューを誰がするか（森の成果物は稲田（要確認）、上田・小澤の成果物は森がレビューする想定）。

## 現時点の方向性
- Geminiメモは「開発者自身がテスト設計をしっかり行い、レビューを経てテストを実施する」としているが、文字起こしでは佐々木の提案（案A）であり、野澤は案Bの現実性も示している。合意かどうかは要確認。
- Web側のテストコード方針は、月曜の会議で協議する。
