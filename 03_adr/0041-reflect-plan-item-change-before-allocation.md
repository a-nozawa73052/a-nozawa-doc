# ADR-0041: 引き当て前のプラン変更・品目変更を、出荷依頼に反映できるようにUDSを改修する

- 決定者・関係者: 野村拓史、野澤有沙（UDS）、阿部昭彦、井上充
- 出典: 文字起こし 00:00:00〜00:10:18（Geminiメモ: https://docs.google.com/document/d/1c7U79nHs9wm4kADcZrCu6SduhDe9Ocxc9kpyt9I65cg）
- 備考: 工期は未確定。野澤が開発メンバーと確認して回答する。

## コンテキスト
- 営業が数や色を間違えて、NeOSで明細変更をかけることがある。特にカメラで多い（阿部）。
- 現状、NeOSで契約がキャンセルされると、引き当て前であれば、UDSの画面から引き当て依頼が表示されなくなる（非表示）。
- 一方、プラン変更は、UDSに契約が取り込まれて出荷依頼ができたあとにかかっても、その出荷依頼には反映されない（野澤）。
- UDSはNeOSから「数量」という値を受け取っておらず、数量の項目もない。UDSは品目（NeOS品目CD）で個数を判断している（野澤）。
- 阿部の認識では、当日の修正は効くが、翌日以降は修正が効かず、キッティング依頼のままになる。
- 野村の見立てでは、翌日以降は営業が契約をキャンセルして新しい契約を起票していて、旧契約と新契約の両方の機材が表示されている可能性がある（要確認）。

## 決定
- 引き当て前であれば、プラン変更と品目修正を出荷依頼に反映する。キャンセルを反映しているのと同じ扱いにする。
- 反映後は、引き当て時に最新の正しいプランで引き当てる。
- 引き当て前の反映ができていない現状は、バグに近いものとして扱う。

## 理由
- 野村と野澤が、あるべき仕様は「引き当て前なら反映する」で合意した。
- 野澤は、引き当て前であればプラン変更を反映しても問題ない、開発上のリスクはないと判断している（野澤: 「これはリスクないと思いますね」）。
- プラン間違いは優先ミュージックなどでも起きる（野村）。

## 影響・トレードオフ
- 現状は、シッピング（出荷依頼）をコントラクトと分けて取り込み、一度取り込んだ出荷依頼は出荷まで固定されている（野村の認識）。この固定を、引き当て前に限って更新できるように変える必要がある。
- 引き当て後の扱いは別の論点とする（ADR-0043）。

## 未解決事項・次のアクション
- [ ] [野澤有沙] 引き当て前の品目修正・プラン変更の反映が本当に可能かを開発メンバーと確認し、リスクと工期を週内に報告する。
- [ ] [野澤有沙] 実際の現象（翌日以降の変更時に何が起きているか）を事実確認する（要確認）。

## 補足
- 文字起こしの「迷彩」「明産」は「明細」の誤変換として読み替えた。
- Geminiメモは「翌日になると修正できない」点を阿部の発言として記しているが、阿部自身も「当日は効く、翌日以降はダメだと思う」と推測の口調で話している。事実確認が必要。
