# ADR-0029: ACE移行後の出荷データ（出荷CSV）に、契約先コードと契約先名称を付与する

- 決定者・関係者: 森本風太郎、竹花義人、坪田亜実、野澤有沙（UDS）
- 出典: 文字起こし 00:07:15〜00:13:53、00:15:12〜00:18:36（Geminiメモ: https://docs.google.com/document/d/1uAerVnNIDzQGEfUeSaYWzGdyJzeXFK8u8VAWuLgDjuM）
- 備考: 会議名は「企業名→事業者への変更」だが、会議では付与する値を「契約先コード」と「契約先名称」とすることで合意した。文字起こしの「プロフィット側」「勾配部」など、部署名と思われる語は誤変換の可能性があり、要確認。

## コンテキスト
- キッティングセンター（竹花）は、出荷データの企業名をもとに、人員計画や入荷数の調整のための一括案件の見込みを集計している。
- ACE移行後はデータ構造が大きく変わるため、これまでの企業名と全く同じ使い方はできない（森本）。
- 会議では、「営業が契約をした相手（契約先）」「店舗を運営している事業者」など、企業名の代わりになり得る値が議論された。森本は、今回の見込みの目的には「契約先」が最も適していると提案した。
- 竹花は当初、センター側では、契約先コードと契約先名称が、これまでの企業名と同じように使える情報かどうかを判断できないと答えた。
- 森本は、「同じことができるか」ではなく、「見込みの精度向上に使えるか」という観点で判断してほしいと説明した。営業の事前申告（ADR-0030）と、出荷データの契約先コードを突き合わせて集計する想定である。
- 現行の出荷CSVには、コードは出力していない（野澤）。

## 決定
- ACE移行後の出荷データ（出荷CSV）に、契約先コードと契約先名称の2項目を追加する。
- ACE側は、申込を受けた契約先のコードと名称をデータに含める設計で開発を進める（森本）。
- UDS側は、出荷CSVに契約先コードと契約先名称を出力する。出力列が増えるため、フォーマットが確定したら、野澤が竹花に送付する（野澤）。
- 追加した項目に値が入るのは、運用開始のタイミング（来年春以降のリリース）と同じである。

## 理由
- 営業が契約を結んだ相手の名称で事前申告させ、出荷データの契約先コードで突き合わせると、一括案件を集計・判断できるため（森本）。
- 名称だけだと表記が揺れる。コードを併せて持つと、突き合わせやすくなる（森本: 「マクドナルドって打ってくる人もいれば Mac って打ってくる人もいる…001って明確に宣言させれば、その後当てやすい」）。
- 契約先名の相手を使う以外に適切な値はあまりない（森本）。システム側は今決める必要があるため、先に契約先ベースで開発を進める。

## 影響・トレードオフ
- 出荷CSVの列が増える。竹花は、列の変更に合わせた集計などの後続作業の対応が必要で、準備期間がある程度必要と答えた。
- 1つの一括案件のコードが複数になる可能性について、竹花から質問があった。森本は、営業からの申告がコードごとであれば問題ないとの見解だった。
- 運用調整は、リリース（来年春以降）までに進めればよく、システム側の開発のみ先に進める。

## 検討した代替案
- 店舗を運営している事業者の名称など、契約先以外の値を付与する案 → 可能性としては挙がったが、今回の目的には契約先が最も重要とし、採用しなかった。

## 未解決事項・次のアクション

- [ ] [森本風太郎] 申込を受けた契約先のコードと名称をデータに含める設計で、システム開発を進める。
- [ ] [竹花義人] 出荷データフォーマットの変更に伴い、変更後の形式で集計や後続処理を行えるよう運用準備を行う。
- [ ] 変更後のフォーマットの適用開始時期（何月何日以降か）を、フォーマット確定後に調整する（要確認）。

## 補足
- Geminiメモは、決定事項を「調整済み」として「出荷データへの契約先情報付与と事前申告の導入」を挙げている。文字起こしと大きな食い違いはない。
- 竹花の「センター側では判断できない」という発言は、最終的に「営業側とのルールメイクを進める」ことで了承された。契約先コードと契約先名称が、これまでの企業名と同じ集計に使えるかは、竹花側の運用で確認が必要になる。
