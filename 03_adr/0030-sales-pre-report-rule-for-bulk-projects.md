# ADR-0030: 一括案件は、営業が契約先名称・契約先コードを添えて事前申告するルールを設ける

- 決定者・関係者: 森本風太郎、竹花義人、坪田亜実、野澤有沙（UDS）
- 出典: 文字起こし 00:02:48〜00:07:15、00:13:53〜00:16:10（Geminiメモ: https://docs.google.com/document/d/1uAerVnNIDzQGEfUeSaYWzGdyJzeXFK8u8VAWuLgDjuM）
- 備考: 「5店舗以上」は、森本が「例えばですけど」と挙げた例である。実際の基準（店舗数・件数・機材台数のどれで何以上とするか）は決まっていない。Geminiメモの次のステップには「5店舗以上」と書かれているため、要確認。

## コンテキスト
- 営業からキッティングセンターへの一括案件の情報共有は、ルール化されていない。営業が連携しようと思ったときだけ、Excelやスプレッドシートのリストがチャットなどで届く。共有がないままUDSに依頼が来ることもあり、100%は拾いきれていない（竹花）。
- 竹花は、これまでルール化する想定はなかったと説明した。理由として、一括の線引き（新規の一括、機材リプレイスの一括、チェーン店の一部店舗だけの対応など）が難しいこと、店舗によって機材数が違い、下見をしないと設置台数が決まらない商材があることを挙げた。
- 営業から購買部門への在庫調達目的の共有（文字起こし「勾配部」は誤変換の可能性があり、要確認）は、ルール化されているが、件数・店舗数・機材台数のどれで共有するかは明確になっていない。
- 森本は、見込み精度を高めるなら、事前申告のルールと、出荷データへの契約先名称・コードの付与（ADR-0029）をセットで行わないと効果が上がらないと指摘した。

## 決定
- 営業サイドに、一括案件が発生する際の事前申告のルールを新設する。申告には、契約先名称と契約先コードを含める。
- 申告の対象は、一定店舗数以上の契約や、機材リプレイスなどの一括案件とする。基準の例として「5店舗以上」が挙がった。
- 竹花が営業部門とルールを策定し、周知する。竹花は、営業側にこの申告を求めることは今から始めても問題ないと認識している。
- 運用調整は、来年春以降のリリースまでに進めればよい（森本）。

## 理由
- 契約先名称・コードで事前申告させると、出荷データの契約先コードで集約でき、一括案件と判断できる（森本）。
- 営業が契約先名称・コードで申告するルールがないと、システム側で契約先コードを出力しても、見込みの精度向上につながらない（森本: 「そこのルールが決まらないと、それに合った抽出は用意できない」）。

## 影響・トレードオフ
- 営業側に新たな申告の手間が発生する。
- 竹花は、機材数が分からない段階の申告が多いことを課題として挙げた。森本は、機材数が分からなくても、何店舗以上などまとまった数であれば申告する、という線の引き方を提案した。

## 検討した代替案
- 現状のまま、営業が連携したいときだけリストを共有する → 100%は拾えず、見込み精度が上がらないため、改善の対象とした。
- センター側（キッティングセンター）がルールを定め、合致したときだけ知らせてもらう → 森本が提案した。竹花は、営業側とのルールメイクで対応する方向で了承した。

## 未解決事項・次のアクション
- [ ] [竹花義人] 営業部門に対し、一括案件が発生する際（5店舗以上など）に、契約先名称と契約先コードを事前に申告させる新ルールを策定し、周知する。
- [ ] 事前申告の対象基準（店舗数・件数・機材台数のどれで、何以上とするか）を決める（要確認）。
- [ ] 申告の方法（フォームなど）を決める。森本は「このフォームに契約先名と共に報告してください」というルールを例に挙げた。

## 補足
- Geminiメモは、竹花が当初「センター側でその情報の適性が判断できない」としたが、ルールの前提を確認したうえで、営業サイドとのルールメイクを進めることで合意した、としている。文字起こしと矛盾はない。
- 文字起こしの「ローカルのコミュニケーション」は、営業のローカルなチャットなどを指すと解釈した。
