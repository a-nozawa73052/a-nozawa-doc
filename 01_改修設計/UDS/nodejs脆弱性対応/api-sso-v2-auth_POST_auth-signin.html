データ構造 リクエスト・レスポンス・参照先

リクエスト

POST /v2/auth/signin
Content-Type: application/json

{
  "userName": "test@example.com",
  "password": "SecurePassword123",
  "serviceCodes": "G30"
}

認証前のAPIのため、x-umid と Authorization ヘッダーは不要です。serviceCodes はカンマ区切りで複数指定できます（例："G30,ABC,DEF"）。

R01

仕様確認サービスが利用できないときのステータスコード

内容

共通の 400（BadRequest）の説明に「ユーザーがサービス利用不可」とあります。一方で、signIn の 401 は「認証・認可失敗」です。サービスが利用できないとき（No.29・30）に 400 と 401 のどちらを返すかが決まりません。

対応方針

本書は 401 と仮定しています。【確認先・期限】

R02

仕様確認複数のサービスコードを指定したときの判定

内容

"G30,ABC,DEF" のように指定したとき、すべてのサービスが有効なら成功なのか、1つでも有効なら成功なのかが書かれていません。空要素（"G30,,ABC"）や前後の空白の扱いも不明です。

対応方針

確認後、No.3 を確定し、一部だけ有効・空要素の項目を追加します。【確認先・期限】

R03

仕様確認有効期間の境界と日付の基準

内容

開始日・終了日の当日を期間に含むか、日付を日本時間で比較するかが書かれていません。serviceDeactivationDate が未設定（無期限）のときの扱いも不明です。

対応方針

本書は「当日を含む・日本時間」と仮定しています（No.20〜24）。無期限の扱いが決まったら項目を追加します。【確認先・期限】

R04

仕様書の修正umid の形式の定義と例が一致しない

内容

SignInResponse.umid は format: uuid ですが、例の 01G22126P8C2XFMZP0C6EQ45RF は26文字の ULID です。ほかのAPIのヘッダーでは ^[0-9A-Z]{26}$ と定義されています。

対応方針

仕様書の format を修正するよう依頼します。テストでは、Members DBの値と一致することだけを確認します（No.2）。
