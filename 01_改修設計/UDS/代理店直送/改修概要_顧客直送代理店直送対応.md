# 改修概要 — 顧客直送・代理店直送対応

**作成日:** 2026-07-07
**対象システム:** uds-web / import_contract（Lambda） / import_direct_shipment（Lambda）
**要望元:** エンターテインメント事業部 和田さん

---

## 1. 背景・課題

| # | 課題 | 内容 |
|---|------|------|
| ① | 代理店直送に対応できない | 契約代行だけでなく施工まで行う代理店（例: エクシング社）へ、USEN MUSICタブレットをKC（キッティングセンター）から直接発送したい。しかしUDS発行の送り状は宛先が「USEN支店」か「顧客」の2択のみで、代理店宛に対応できない。現状はスプレッドシートの管理台帳で代理店発送先を別管理しており、**各部署の工数増・運用ミス**につながっている |
| ② | 顧客直送の送り状に担当者名を書けない | テレマ経由の顧客直送USEN MUSICは、送り状の宛先名が「設置先名」固定で担当者名を追記できない。担当者名がないため店舗側に不審がられ受け取り拒否が発生し、**月100件程度**の再調整が発生している |

> **前提:** 直送には「顧客直送」（既存対応済み）と「代理店直送」（今回新規対応）の2種類がある。

---

## 2. 改修目的

- 送り状の宛先に「代理店発送先」を設定できるようにし、代理店直送に対応する
- 送り状の申し送り事項欄に担当者名等を記載できるようにし、顧客直送の受け取り拒否を減らす
- 上記に伴う検索・マスタ管理・NP審査運用まわりの付随改修を行う

### 4-2. 送り状Excel出力（SBS送り状・福山送り状）の改修

**対象範囲:** uds-web

**現状（As-Is）:**
2系統の出力ロジックが存在し、依頼ごとに「直送対象」か「直送対象外」かで振り分けてから出力データを取得している。

①**直送対象か否かの判定ロジック**（`get_invoice_data()` line 99-124）:

```php
$is_direct_shipments = \Model_Direct_Shipment::find_by_shipping_request_id($id);
// ...
if (!$is_direct_shipments && !in_array($neos_item_pac_cd, $neos_item_pac_cds)) {
    // 直送対象外（request_type_cdに応じてnormal/branchへ）
} else {
    // 直送対象（ship_to_customer）
}
```
- `direct_shipments`テーブルに該当`shipping_request_id`のレコードが**存在するか**で判定している
- `neos_item_pac_cds = ['M0365']`（UNEXTサッカーパック）は別途ハードコードで直送対象扱い

②**出力データの参照先**（判定結果ごとに参照テーブルが異なる）:

| 分岐 | 実装メソッド | 名称 | 住所 | TEL | 郵便番号 |
|------|---------|------|------|-----|---------|
| 直送対象 | `get_data_ship_to_customer()` | `contracts.customer_name` | `contracts.customer_address1/2/3` | `contracts.customer_tel` | `contracts.customer_zip_cd` |
| 直送対象外 | `get_data_non_direct_shipment()` | `branch_replacement.shipping_name` | `branch_replacement.shipping_address1/2/3` | `branch_replacement.shipping_tel` | `branch_replacement.shipping_zip_cd` |

`get_data_ship_to_customer()`（line 219-254）では`shipping_requests`に`contracts`を`contract_cd`でLEFT JOIN済み（line 242-244）のため、`contracts`の代理店発送先カラムはこのJOINにそのまま乗せられる。

- SBS送り状（東エリア）: `classes/download/excel/center/east/invoice.php`
  - 判定ロジック `get_invoice_data()`: line 99-124
  - `get_data_ship_to_customer()`: line 219-254
  - `get_data_non_direct_shipment()`: line 157-192
- 福山送り状（西エリア）: `classes/download/excel/center/west/invoice.php`（同名メソッド、同様の構成。行番号は着手時に東エリアと突き合わせて確認すること）
- トリガー: `modules/manage/classes/controller/center/shipment.php` の `action_download_save()`（line 69、管轄支店CDでSBS/福山を判定）
- `shipping_requests.shipping_message` カラムは既存（Model_Shipping_Request line 39）だが、現状この2ファイルの送り状出力では未使用（直送CSV出力では使用済み）

**変更仕様（To-Be）:**

**① 直送対象か否かの判定ロジック：変更なし**
`direct_shipments`テーブルの存在チェックはそのまま維持する。`M0379`（代理店直送）はimport_contract側の中カテ判定に追加され（4-7節①）、これまで通り`direct_shipments`に登録されるため、この判定ロジックに手を入れる必要はない。

> **⚠️ 検討の経緯:** 当初は「直送案件対象品目マスタ」参照への変更を検討したが、そのマスタは「プロ業のNP審査抽出」という別用途のカテゴライズであり、USEN MUSIC自体の品目データが登録される見込みがなく、事業部確認待ちがブロッキングになっていた。`direct_shipments`は本改修が直接コントロールできるテーブルであるため、判定を変更しない方針に変更した。

**② 顧客直送か代理店直送かの判定ロジック（新規）**
直送対象と判定された場合、さらに`direct_shipments`の新カラム**`shipment_type_cd`**（1:顧客直送 / 2:代理店直送）を参照して判定する。このカラムはimport_contractが`direct_shipments`にINSERTする時点でセットする（4-7節①）。

```php
// 新規
$shipment_type_cd = \Model_Direct_Shipment::get_shipment_type_cd_by_shipping_request_id($id);
// 1: 顧客直送 / 2: 代理店直送 / null: direct_shipmentsレコードなし（＝M0365等、顧客直送扱いにフォールバック）
```

> **⚠️ M0365（UNEXTサッカーパック）の扱い:** `M0365`はdirect_shipments登録対象の中カテ（4-7節①）に含まれていないため、`direct_shipments`レコード自体が存在しない。この場合は`shipment_type_cd`が取得できないため、**顧客直送として扱う**（既存動作を維持するフォールバック）。

> **参考:** `direct_shipment.tsv`（4-6節・import_direct_shipment）は**顧客直送の場合のみNeOSから連携される**（代理店直送では連携されない）。そのため`shipping_requests.shipping_destination`は代理店直送のレコードでは常に空になる想定。

**③ 出力項目の参照先変更**
`get_data_ship_to_customer()`のSQLに`direct_shipments`をLEFT JOINし（`direct_shipments.shipping_request_id = shipping_requests.id AND direct_shipments.deleted_at IS NULL`）、取得した`shipment_type_cd`に応じて参照先を分岐する。

- **名称／名前**のみ3パターン分岐（顧客直送の場合に`shipping_requests.shipping_destination`という新しい参照先が加わるため）
- **住所・TEL・郵便番号**は2パターン分岐（`direct_shipment.tsv`には住所・TEL・郵便番号の情報がなく、顧客直送では従来の`customer_*`を使うしかないため）

### 4-3. マスタ管理画面：直送マスタ2種のアップロード・ダウンロード機能追加

**対象範囲:** uds-web（マスタ管理画面「その他マスタ更新」の一番下）

**現状（As-Is）:** 既存マスタは以下の定型パターンで実装されている（例: 支店在庫マスタ）。

- コントローラ: `modules/manage/classes/controller/master/other.php`（アップロード: line 42-107、ダウンロード: line 280-361）
- ビュー: `modules/manage/views/master/other/index.php`
- アップロード: `classes/upload/csv/base.php`（基底） / `classes/upload/csv/master/branch/stock.php`（実装例）
- ダウンロード: `classes/download/csv/base.php`（基底） / `classes/download/csv/master/other/stock.php`（実装例）
- モデル: `classes/model/head/branch/stock.php`

**変更仕様（To-Be）:** 「直送カテゴリマスタ」「直送案件対象品目マスタ」を新規追加する。既存の`Upload_Csv_Base`／`Download_Csv_Base`基盤を踏襲し、以下の仕様とする（受領したCSVサンプルに準拠）。**このマスタは「プロ業のNP審査抽出」用途のままで、4-2節の直送対象・顧客直送/代理店直送判定には使用しない**（4-2節参照）。

**アップロード仕様:**
- CSV形式（1行目ヘッダー、Shift-JISエンコード。`Upload_Csv_Base::parse()`が読込時にUTF-8へ変換する既存仕様に準拠）
- 直送カテゴリマスタ: `制御コード, カテゴリCD, カテゴリ名` の3列
- 直送案件対象品目マスタ: `制御コード, カテゴリCD, NeOS契約品目CD, NeOS契約品目名` の4列
- 取込方式は**行単位のUPSERT＋論理削除**とする（全件洗い替えは行わない）。既存の支店在庫マスタ（`Upload_Csv_Master_Branch_Stock::save_line()`）と同様のパターンで実装する
  - 制御コード（`validate_control_code()`で`0`／`1`／空のみ許可）が`1`の行 → ユニークキー（直送カテゴリマスタ: `category_cd`／直送案件対象品目マスタ: `neos_item_cd`）に一致する既存レコードを論理削除（`deleted_at`を更新）
  - 制御コードが`1`以外の行 → ユニークキーで既存レコードを検索し、存在すれば更新（差分がある場合のみ）、存在しなければ新規登録
    - 「存在するか」の判定は**論理削除済みレコードも含めて**行う（`category_cd`／`neos_item_cd`のUNIQUE制約は`deleted_at`に関わらず有効なため、論理削除済みのキーが物理的に残ったままINSERTすると制約違反になる）。論理削除済みのキーが再登録された場合は、内容の差分に関わらず更新扱いとし、`deleted_at`をNULLに戻して復活させる
  - **CSVに含まれない（アップロードされなかった）既存レコードはそのまま残る**（更新も削除もされない）

> **要確認:** `M0365`（UNEXTサッカーパック）は`direct_shipments`登録対象の中カテに含まれないため、この契約には`direct_shipments`レコード自体が存在せず`shipment_type_cd`も取得できない。送り状出力側（4-2節②）で「レコードなし＝顧客直送」のフォールバックを実装することで対応する。

---

> `contracts`の`agency_*`系7カラムは全て**NULL許容**（`DEFAULT NULL`）で確定。代理店直送でない契約行では`NULL`のままになる。
