## 1. 各環境マージ順

dev→stg→mainのマージは不可能
3機能（SIM管理・代理店対応・URX-05QR）が、環境ごとに**異なる順序**でマージされる予定のため。

| 環境 | 1番目 | 2番目 | 3番目 |
|---|---|---|---|
| **dev** | SIM管理（マージ済み） | 代理店対応（8/31） | URX-05QR（9/14） |
| **stg** | 代理店対応（9/7） | URX-05QR（9/28） | SIM管理（10/12） |
| **main** | 代理店対応（9/28） | SIM管理（10月末） | URX-05QR（11月） |

devではSIMが最初だが、stg・mainでは代理店対応が最初かつSIMが最後――という具合に、3環境で並び順がバラバラになる。この状態でうっかり`develop → staging`や`staging → main`のブランチマージを行うと、まだそのタイミングでは反映したくない機能まで一緒に持ち込んでしまう。そのため、**各機能を個別にcherry-pick（部分反映）する**方式を、3機能×3環境ぶん繰り返す必要がある。

### ② SIM管理（#252・#298）

developにはすでに通常マージ（squashではない）で入っているため、代理店対応のような「squashコミット1個をcherry-pick」という単純な形にはできない。stg・mainでそれぞれ以下の対応を取る。

**stg（10/12）: develop→stagingの通常のPRマージでよい**

**前提条件（要維持）:** 10/12時点で「develop＝SIM管理＋代理店対応＋URX-05QRのみで、他に何も追加されていない」状態にすること。

この前提が保たれていれば、10/12時点でstagingは既に代理店対応・URX-05QRをcherry-pick済みで保有しており、developも同じく代理店対応・URX-05QRを保有（＋SIM管理）している。つまりdevelopとstagingの差分は**SIM管理の分だけ**になるため、`develop → staging`のPRを作成して素直にマージすればよい。`-m 1`でのマージコミットcherry-pickは不要。

> ⚠️ 10/12までの間に、今回の3機能と無関係な別PRがdevelopにマージされた場合、この前提が崩れる。その場合は素直なマージではなく、下記mainと同様の`-m 1`cherry-pick方式に切り替えること。

**main（10月末）: 通常マージ不可、`-m 1`でのcherry-pickが必要**

10月末時点でmainは**代理店対応のみ**保有しており、URX-05QRはまだ（mainのURX-05QR反映は11月予定）。一方developは9/14時点でURX-05QRを既にマージ済みのため、この時点で`develop → main`の通常マージを行うと、SIM管理と一緒にURX-05QRまで先走ってmainに入ってしまい、mainの希望順序（代理店対応→SIM管理→URX-05QR）が崩れる。そのため、mainへは**マージコミットそのものを`-m 1`オプション付きでcherry-pick**する方式を使う。

```bash
# developにマージされた順番の通りに、2つのマージコミットを順にcherry-pick
git cherry-pick -m 1 fd8d560dfa3535c741472177ac43fab9acfe8116   # #252のマージコミット
git cherry-pick -m 1 43e42d7d731caa8012408f0a6e0d4673399e2f8e   # #298のマージコミット
```

`-m 1`は「マージコミットの第1親（＝マージされる前のdevelopの状態）を基準に、このマージが実際に持ち込んだ差分」を計算してcherry-pickするためのオプション。これにより、PR内の個々のコミットを1つずつ拾わなくても、マージ時点の正味の差分だけを、URX-05QRを巻き込まずに移植できる。

## 5-1. 例外対応：mainへの緊急ホットフィックス（`is_branch_cd`への1行追加）

`config/define.php`の`is_branch_cd`配列に`'3' => '2105010000',`を追加する緊急対応が発生。以下の方針で対応する。

- **main**: 直接ホットフィックスとして反映（`hotfix/is-branch-cd-add-entry`ブランチ、`origin/main`起点で作業中）
- **develop**: 同じ1行を別PRでバックポートする
- **staging**: 個別の反映は行わない。10/12のSIM管理反映（`develop → staging`マージ）時に、developにバックポート済みのこの1行も自然に一緒に入る想定

**この例外がなぜ安全か:** `is_branch_cd`は代理店対応・SIM管理・URX-05QRのいずれも触っていない配列であり、ファイル内の別の場所（別配列）への単純な1行追加のため、既存の3機能とのコンフリクトは発生しない。

**「developの凍結」との関係:** このホットフィックスをdevelopにバックポートすると、厳密には「developは3機能のみ」という前提から外れる。ただし上記の通りコンフリクトの心配がない変更と確認済みのため、**10/12の`develop → staging`の通常PRマージは、この1行を含めてそのまま実施してよい**（この1行の分だけ、SIM管理との差分に追加されるだけ）。この例外はここに記録した1件のみとし、これ以外の変更がdevelopに追加された場合は改めて個別に安全性を確認すること。

## 5. 今後の確認事項・注意点

- **URX-05QR開発後**: 代理店対応（stg・mainとも既に反映済みの想定）・SIM管理との**ファイル重複調査を必ず実施**する
- **develop の凍結維持（最重要）**: 10/12まで、developには代理店対応・URX-05QR・SIM管理・上記5-1のホットフィックス以外の変更を追加しないこと。これが崩れると、10/12のstg反映を素直な`develop → staging`マージで行えなくなり、mainと同様の`-m 1`cherry-pick方式に切り替える必要がある
- **10/12のstg反映（SIM管理）**: マージ前に`git diff origin/staging origin/develop`等で、本当にSIM管理分だけが差分として出ているか（他の変更が紛れ込んでいないか）を確認してからPRを作成する
- **各cherry-pick後は必ず`git diff origin/<反映先ブランチ>`で最終差分を確認**し、意図した機能の内容だけが反映されているか（他機能の内容が紛れ込んでいないか）を目視チェックする
- **将来的な収束**: 11月末時点で、dev・stg・mainの3環境すべてに3機能全てが揃う想定。それ以降は通常のdev→stg→mainのブランチ昇格に戻せる見込み
