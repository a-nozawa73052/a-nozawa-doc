# 新卒研修課題：UDS問い合わせ仕分けチャットボットの開発

| 項目 | 内容 |
|------|------|
| 対象 | 新卒（1名） |
| 期間 | 8週間 |
| 対象システム | UDS（USEN Distribution System） |

## 1. 背景

UDS（USEN Distribution System）は、端末の引き当て・キッティング・出荷・施工を管理するシステムです。UDS開発チームには日々さまざまな問い合わせが届きますが、その中には次のようなものが混ざっています。

- 依頼者自身が**マスタの登録・更新で解決できるもの**
- **UDS開発の担当ではない**もの（NeOS・UNIS・SGS・物流・事業部などが担当）
- 本当に**UDS開発の対応が必要なもの**

これらをすべて開発者が受けて仕分けているため、開発者の負担になっており、依頼者も回答を待つ時間が長くなっています。

## 2. 目的

- 問い合わせを自動で仕分け、依頼者に「次に何をすればいいか」をすぐに案内する
- 開発の過程で、**UDS業務の理解**と**AWSのサーバーレス構成・生成AI（RAG）の基礎**、**評価にもとづく改善の進め方**を身につける

## 3. 分類の定義

| 分類 | 判定の目安 | ボットの返答 |
|------|-----------|------------|
| **① 自己解決** | マスタの登録・更新や画面操作で解決できる | 対象の画面と手順を案内する |
| **② 問い合わせ先が別** | UDS開発以外のチーム・システムが担当している | 問い合わせ先（チーム名・チャンネル名）と、伝えるべき情報を案内する |
| **③ UDS開発の対応が必要** | 不具合の疑い、データの直接修正、仕様変更 | 開発対応が必要であることを伝え、問い合わせに含めるべき情報（依頼ID・画面・発生日時・エラー内容など）を提示する |
| **④ 判断できない** | 情報が足りない | 追加で質問する。それでも決まらなければ③として扱う |

> **最重要ルール：迷ったら③に倒す。**
> 本当は不具合なのに①と判定すると、依頼者がマスタを操作してデータをさらに壊すおそれがあります。

## 4. 要件

### 必須要件

| No | 要件 |
|----|------|
| M1 | 問い合わせ文を①〜④に分類し、分類結果を表示する |
| M2 | 分類ごとに決められた形式で回答する |
| M3 | 回答の根拠となったドキュメント名を表示する |
| M4 | 分類の確信度が低い場合は①と答えず、④または③にする |
| M5 | 問い合わせ文・分類結果・確信度・回答をログとして保存する（改善の分析に使う） |
| M6 | ブラウザから使える簡易画面がある |
| M7 | 構成をIaC（AWS CDK または SAM）で管理する |

### 任意要件

- 回答に「役に立った／立たなかった」のフィードバックボタンを付ける
- ③と判定したときに、開発チームへの問い合わせ文の下書きを自動で作る
- Cognitoでログイン制御する
- ナレッジのドキュメントをS3に置いたら自動で再取り込みする

## 5. 設計方針

### 二段階方式（基本形）

```
問い合わせ文
   │
   ▼
[ステージ1：分類]  判断基準ドキュメントを参照し、分類・確信度・理由・不足情報をJSONで出力
   │
   ▼
[ステージ2：回答]  分類に応じたナレッジを検索し、分類ごとのプロンプトで回答を作る
```

分類と回答を分けることで、**分類の精度だけを測って改善できる**ようにします。

### ルールの追加（改善フェーズ）

評価で見つかった誤分類をもとに、「エラー」「消えた」「反映されない」などの危険なキーワードを含むものは**ルールで強制的に③にする**処理を、ステージ1の前に追加します。

```
問い合わせ文 → [ルール判定] →（該当すれば③で確定）
                   │ 該当しない
                   ▼
              [ステージ1] → [ステージ2]
```

## 6. 想定構成

```
[ブラウザ] → [Amplify Hosting（静的画面）]
                ↓
         [API Gateway] → [Lambda]
                           ├→ [Bedrock（Claude）]          … 分類・回答の生成
                           ├→ [Bedrock Knowledge Bases]    … ナレッジ検索
                           │       ↑
                           │   [S3（ドキュメント）]＋[S3 Vectors]
                           └→ [DynamoDB]                   … 問い合わせログ（M5）
```

## 7. ナレッジ（自分で作る）

| ドキュメント | 内容 | レビュー担当 |
|------------|------|------------|
| 開発対応の判断基準 | ①〜④の判定ルールと具体例 | 指導者 |
| マスタ操作手順書 | どのマスタを、どの画面で、どう登録・更新するか | UDS業務担当者 |
| 問い合わせ先一覧 | 内容ごとの担当窓口（**チーム名・チャンネル名で書き、個人名は書かない**）と、伝えるべき情報 | 指導者 |
| 既存のUDSドキュメント | 用語集、依頼IDの採番ルールなど（指導者が指定する） | － |

## 8. テストセット

- 指導者から渡される過去の問い合わせ実績から**50件以上**を選び、それぞれに正解の分類を付ける
- ①〜④が偏らないように選ぶ（特に③を十分に含める）
- テストセットは**ナレッジには入れない**（答えを覚えさせると正しく評価できないため）

## 9. 評価指標

| 指標 | 目標 |
|------|------|
| **③を①と誤判定した件数** | **0件（最重要）** |
| 分類の正答率 | 80%以上を目安とする |
| 混同行列 | どの分類同士を間違えやすいかを分析する |
| 回答の妥当性 | ①の手順、②の窓口が正しいかを指導者がサンプルで確認する |

## 10. スケジュール（8週間）

| 週 | 内容 | 成果物 |
|----|------|--------|
| 1 | UDS業務の学習、AWSの基礎学習、**AWS Budgetsでの予算アラート設定** | 学習メモ |
| 2 | ナレッジの作成（判断基準・問い合わせ先一覧・マスタ操作手順書） | ナレッジ一式（レビュー済み） |
| 3 | テストセットの作成、ステージ1（分類）の試作と初回評価 | テストセット、初回の評価結果 |
| 4 | Knowledge Basesの構築、ステージ2（回答）の実装 | 分類と回答が動く状態 |
| 5 | Lambda・API Gateway・画面・ログ保存の実装、IaC化 | ブラウザから使える状態 |
| 6 | **中間発表**、評価（混同行列）、誤分類の分析 | 中間発表資料、評価レポート初版 |
| 7 | 改善：ルール判定の追加、プロンプトとナレッジの見直し、再評価 | 改善前後の比較 |
| 8 | 仕上げ、README整備、**最終発表**、リソースの後片付け | 最終成果物一式 |

## 11. 最終成果物

1. ソースコード（IaCを含む）とREADME（構築手順・構成図）
2. ナレッジ一式
3. テストセットと評価レポート（混同行列、誤分類の分析、改善前後の比較）
4. 最終発表（デモを含めて20分程度）

## 12. 評価基準（研修としての評価）

| 観点 | 見るポイント |
|------|------------|
| 業務理解 | 判断基準・問い合わせ先一覧が実際の業務に合っているか |
| 安全性 | 「迷ったら③」が設計と評価に反映されているか |
| 技術 | 構成の妥当性、IaC化、コストへの配慮 |
| 改善プロセス | 誤分類の原因を分析し、仮説を立てて検証したか |
| 伝える力 | README・発表の分かりやすさ |

## 13. 制約・注意事項

- ナレッジとテストセットには、**指導者が渡したデータだけ**を使う
- ベクトルストアは**S3 Vectors**を使う（OpenSearch Serverlessは固定費が高いので使わない）
- 研修用AWSアカウントで作業し、研修終了時にリソースを削除する
