# UX設計：スマホ版UDS — 入庫処理・回収済み処理

**作成日:** 2026-06-01  
**前提:**
- デバイス：社用iPhone（iOS Safari）
- アクセス：VPN（AnyConnect）経由、QRコード読み取りでURLへアクセス
- バーコード読み取り：カメラAPI、またはBluetoothバーコードスキャナー（HIDキーボードエミュレーションモード）のどちらか（併用可）。実機検証でカメラでは小型バーコードを読み取れない可能性が判明したため、2026-09にBluetoothスキャナー対応を追加
- 一括処理：複数読み取り後、ボタン押下で一括実行
- エラー時：エラー端末のみ報告し、成功分は処理を確定する

---

## 1. 画面一覧

| 画面ID | 画面名 | URL |
|--------|--------|-----|
| M-01 | 機能選択画面 | `/mobile/branch/store?token={支店ごとの不透明トークン}`（2026-09〜。`branch_cd`は直接URLに含めない。詳細は開発概要書「QRコードURLのアクセストークン化」参照） |
| M-02 | バーコード読み取り画面（入庫処理） | 同URL内でJSにより画面切り替え（SPA方式） |
| M-03 | バーコード読み取り画面（端末回収登録） | 同URL内でJSにより画面切り替え（SPA方式） |
| M-04 | 処理結果画面 | 同URL内でJSにより画面切り替え。`/mobile/branch/store/execute`のJSONレスポンスを元に描画 |
| E-01 | エラー画面（トークン不正） | 同URL。サーバー側で`token`を検証し、初回表示時に出し分け |

    :何も表示せず破棄\n（次の入力を待つ）;
  else (はい＝スキャナー由来と判定)
  endif

| 項目 | 内容 |
|------|------|
| セグメントボタン | 「📷 カメラ」「📡 スキャナー」の2択。選択中の方を色付きで強調表示。タップで即座に画面下部の内容が切り替わる |
| 初期選択状態 | 「カメラ」を初期選択とする（前回の選択を端末に記憶する等は行わない。画面を開くたびに「カメラ」から始まる） |
| カメラ選択時の表示 | 既存の「バーコードを読み取る」ボタンのみ表示。Bluetooth入力欄・接続案内は非表示 |
| カメラ起動 | タップするとカメラ起動（ハーフモーダルでカメラプレビューを表示） |
| 読み取り成功時（カメラ） | ビープ音 + バイブレーション → リストに追加 → カメラ継続起動 |
| スキャナー選択時の表示 | Bluetooth接続案内ブロック＋読み取り待機表示を表示。カメラボタンは非表示 |
| Bluetooth接続案内ブロック | ペアリング手順（設定アプリでのBluetooth接続手順）を箇条書きで表示。タップで開閉できる（一度確認したら閉じておける）。**実際にペアリング済みかどうかをアプリ側から検知することはできない**ため、あくまで案内であり、常時表示するかどうかはユーザー操作に委ねる |
| 手入力の防止（重要） | タップ可能な入力欄は画面上に表示しない（手入力の誘因を作らないため）。実際にスキャナーの入力（OSレベルではキーボード入力として届く）を受け取るための入力欄は、画面上は見えない形で裏側に常時フォーカスしておく。**入力元がスキャナーか手入力かをアプリ側から完全に判別する方法は存在しない**が、以下の速度チェックで手入力をほぼ確実に排除する： 先頭文字の入力からEnterまでの合計時間が300ミリ秒を超えた場合は手入力とみなし、**エラー表示は出さずに黙って入力を破棄する**（バーコードスキャナーは1件分の文字列を数十ミリ秒で送信するため、人間の入力速度とは明確に区別できる） |
| 読み取り成功時（Bluetoothスキャナー） | 入力欄への自動入力（Enter付加）を検知し、速度チェックを通過 → リストに追加 → 入力欄をクリアしてフォーカス維持 |
| 重複読み取り | カメラ・Bluetoothどちらでも、同一シリアルコードを再読み取りした場合はトースト表示「すでに読み取り済みです」でスキップ |
| 読み取りリストの扱い | セグメントボタンを切り替えても、読み取り済みリストの内容は保持する（カメラで数件読んだ後にスキャナーへ切り替えて続きを読む、という使い方も可能） |
| 削除ボタン（╳） | リストから1件削除 |
| 実行ボタン | 読み取り件数が0件のときは `is-disable` |
| 実行ボタンラベル | 機能に応じて「入庫処理する（N件）」「回収済みにする（N件）」 |
| 実行前確認 | 確認ダイアログは出さない（タップ操作の流れを止めない）※ 処理結果で確認できるため |

## 5. バーコード読み取り実装方針（カメラ／Bluetoothスキャナー）

### 5-0. Bluetoothスキャナー対応（追加）

実機検証で、社用iPhoneのカメラでは小型のバーコードを読み取れない可能性が判明したため、BUSICOM BC-BS801D-V2-CWによるBluetooth読み取りにも対応する。

- **接続方式**：Bluetooth HID（キーボードエミュレーション）モード。本製品はデフォルトでHIDモードのため機器側の追加設定は不要
- **アプリ側の実装**：Web Bluetooth API等は使用しない（iOS Safari非対応のため）。M-02/M-03画面に常設のテキスト入力欄を用意し、画面表示中は常にフォーカスを維持する。スキャナーが読み取ったシリアルコードは、OSレベルでキーボード入力として入力欄に送信される（末尾にEnterキー相当の入力が付加される初期設定）。JS側は入力欄の`keydown`イベントで`Enter`を検知し、その時点の入力値をカメラ読み取りと同じ`addSerial()`処理に渡す
- **iOSの画面キーボード非表示化**：入力欄に`inputmode="none"`を指定し、タップしてもiOS標準の画面キーボードが出ないようにする（物理的な画面キーボードスペースを占有させず、常時Bluetooth入力を受け付ける状態を保つため）
- **事前準備（運用）**：社用iPhoneの「設定」→「Bluetooth」でスキャナーと事前ペアリング。iPhoneのキーボード言語を「英語（米国）」に設定（メーカー仕様）
- **カメラとの共存**：カメラボタンとBluetooth入力欄は同一画面に常時両方表示し、どちらで読み取っても同じ読み取りリストに追加される。カメラのモーダルを開いている間もBluetooth入力欄は裏側で機能する想定（モーダルを閉じたタイミングで入力欄にフォーカスを戻す）

### 5-1. カメラAPI実装方針

### ライブラリ選定（要確認）

iOSのSafariは `BarcodeDetector` APIの対応が不安定なため、ライブラリを使用する。

| ライブラリ | iOS Safari対応 | 備考 |
|-----------|---------------|------|
| `@zxing/browser` | ◎（iOS 14.3+） | WebRTC使用。**Code 128対応。採用決定** |
| `quagga2` | ○ | 旧Quaggaの後継。軽量 |
| `html5-qrcode` | ◎ | ラッパーライブラリ。導入が簡単 |

→ **`@zxing/browser` に決定**（バーコード種類：Code 128 確認済み。実機での動作確認は開発時に実施）

**実装メモ：** 本リポジトリはnpm/webpack等のビルド構成を持たず、jQuery等の既存ライブラリも静的ファイルとして配置する慣習のため、`@zxing/browser`も同様にベンダリングする。ただし同ライブラリはUMD（ブラウザグローバル）ビルドを提供していないため、ESモジュール形式（`<script type="module">`）で読み込む方式を採用し、依存関係（`@zxing/library`, `ts-custom-error`）を含めて`public/assets/js/vendor/`配下にオフラインで動作するよう相互参照を書き換えて配置した。

### 読み取りフロー（JavaScript）

```
1. 「バーコードを読み取る」ボタン押下
        ↓
2. カメラ起動許可ダイアログ（初回のみiOSが表示）
        ↓
3. ハーフモーダル内でカメラプレビュー開始
        ↓
4. バーコード検出
    ├─ 新規シリアルコード → リストに追加 + 効果音/バイブ → カメラ継続
    └─ 重複シリアルコード → トースト「すでに読み取り済みです」→ カメラ継続
        ↓
5. 「閉じる」ボタン押下でモーダルを閉じ、実行ボタン押下へ
```

### 確認が必要な事項

- UDSで使用しているバーコードの種類（Code 128 / Code 39 / その他）
- iOSのSafariのカメラ許可設定（MDM管理端末のため制約がある可能性）
- AnyConnect VPN接続中のカメラAPIへの影響
- Bluetoothスキャナー（BC-BS801D-V2-CW）接続中に、AnyConnect VPN接続やMDM管理端末の制約でBluetooth自体が制限されないか
- Bluetoothスキャナーの送信モード設定（初期値「同期送信」でよいか、「非同期送信」に変更するか）

## 7. APIエンドポイント（新規）

| メソッド | URL | 処理 |
|---------|-----|------|
| GET | `/mobile/branch/store?token={支店ごとの不透明トークン}` | 初期画面表示（tokenをサーバー側で検証し、M-01〜E-01を含むHTMLを返す） |
| POST | `/mobile/branch/store/execute` | 一括処理実行（JSON API） |

### POSTリクエスト（`/mobile/branch/store/execute`）

```
token      : {支店ごとの不透明トークン}（branch_cdはクライアントから直接送信しない。
              サーバー側でtokenから毎回branch_cdを再解決することで、branch_cdを
              直接POSTして認可チェックを迂回されることを防ぐ）
type       : store（入庫処理）または return（回収済み）
serials[]  : {シリアルコード1}, {シリアルコード2}, ...
```

### レスポンス（JSON）

```json
{
  "success_count": 2,
  "error_count": 1,
  "notice_count": 1,
  "errors": [
    {
      "serial_cd": "XYZ112233445",
      "message": "該当のシリアルコードが見つかりません"
    }
  ],
  "notices": [
    {
      "serial_cd": "QRS998877665",
      "message": "この端末はキャンセル返却予定のため、回収登録できません。担当者にご確認ください。"
    }
  ]
}
```

`notices[]` はキャンセル返却予定端末（`device_status_cd=18`）が対象で、入庫処理・回収処理どちらでも発生しうる。エラーとは異なりステータス更新は行わず、「続けて処理する」時もリストへ復元しない。
