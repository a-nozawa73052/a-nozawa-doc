# UX設計：スマホ版UDS — 入庫処理・回収済み処理

**作成日:** 2026-06-01  
**更新：** 2026-10-14 実装コードのレビュー結果を反映し、URL・画面構成・トークン方式・キャンセル返却予定端末の扱い・回収報告コメント・Bluetooth接続案内の扱いを実装内容に合わせて全面修正
**前提:**
- デバイス：社用iPhone（iOS Safari）
- アクセス：VPN（AnyConnect）経由、QRコード読み取りでURLへアクセス
- バーコード読み取り：カメラAPI、またはBluetoothバーコードスキャナー（HIDキーボードエミュレーションモード）のどちらか（併用可）。実機検証でカメラでは小型バーコードを読み取れない可能性が判明したため、2026-09にBluetoothスキャナー対応を追加
- 一括処理：複数読み取り後、ボタン押下で一括実行
- エラー時：エラー端末のみ報告し、成功分は処理を確定する

**仕様:**

| 項目 | 内容 |
|------|------|
| セグメントボタン | 「📷 カメラ」「📡 スキャナー」の2択。選択中の方を色付きで強調表示。タップで即座に画面下部の内容が切り替わる |
| 初期選択状態 | 「カメラ」を初期選択とする（前回の選択を端末に記憶する等は行わない。画面を開くたびに「カメラ」から始まる） |
| カメラ選択時の表示 | 既存の「バーコードを読み取る」ボタンのみ表示。Bluetooth接続案内は表示しない |
| カメラ起動 | タップするとカメラ起動（ハーフモーダルでカメラプレビューを表示） |
| 読み取り成功時（カメラ） | リストに追加 → カメラ継続起動 |
| スキャナー選択時の表示 | 読み取り待機の表示のみ（2026-10-14修正：接続案内ブロックは画面に表示しない。ペアリング手順はユーザーマニュアルに記載する）。カメラボタンは非表示 |
| 手入力の防止（重要） | タップ可能な入力欄は画面上に一切表示しない（手入力の誘因を作らないため）。実装では専用の入力欄は用意せず、画面全体のキー入力イベントを「スキャナー」選択中のみグローバルに監視し、`input`/`textarea`/`select`等にフォーカスしている場合は無視する。**入力元がスキャナーか手入力かを完全に判別する方法は存在しない**ため、以下の速度チェックで手入力をほぼ確実に排除する：直前の入力から120ミリ秒以上間隔が空いたら新しい読み取りとしてバッファをリセットし、150ミリ秒入力が無ければバッファを破棄する。バーコードスキャナーは1件分の文字列を数十ミリ秒で連続送信するため、人間の入力速度とは明確に区別できる（2026-10-14修正：当初案は「先頭文字からEnterまで300ms」という単一の閾値だったが、実装では上記の2段階の閾値方式になっている） |
| 読み取り成功時（Bluetoothスキャナー） | Enter/Tabキーを検知してバッファを確定 → サーバーの個別バリデーションAPIで存在・ステータスを確認 → OKならリストに追加 |
| 重複読み取り | カメラ・Bluetoothどちらでも、同一シリアルコードを再読み取りした場合はスキップ（リストに追加しない） |
| **一括処理件数の上限** | 読み取りリストは**最大50件**まで。50件に達した状態でさらに読み取ろうとした場合（カメラ・Bluetoothどちらでも）、リストに追加せず「一度に処理できる件数は50件までです」と表示する。⚠️サーバー側（一括実行API）にはこの件数チェックが実装されていない（実装側へ指摘済み。詳細は開発概要書参照） |
| 読み取りリストの扱い | セグメントボタンを切り替えても、読み取り済みリストの内容は保持する（カメラで数件読んだ後にスキャナーへ切り替えて続きを読む、という使い方も可能） |
| 削除ボタン（╳） | リストから1件削除。上限に達していた場合、1件削除すれば再度読み取り可能になる |
| 実行ボタン | 読み取り件数が0件のときは `is-disable` |
| 実行ボタンラベル | 機能に応じて「入庫処理する（N件）」「回収済みにする（N件）」 |
| 実行前確認 | 確認ダイアログは出さない（タップ操作の流れを止めない）※ 処理結果で確認できるため |

## 5. バーコード読み取り実装方針（カメラ／Bluetoothスキャナー）

### 5-0. Bluetoothスキャナー対応（追加、2026-10-14実装に合わせて修正）

実機検証で、社用iPhoneのカメラでは小型のバーコードを読み取れない可能性が判明したため、BUSICOM BC-BS801D-V2-CWによるBluetooth読み取りにも対応する。

- **接続方式**：Bluetooth HID（キーボードエミュレーション）モード。本製品はデフォルトでHIDモードのため機器側の追加設定は不要
- **アプリ側の実装**：Web Bluetooth API等は使用しない（iOS Safari非対応のため）。当初案は専用の常設テキスト入力欄（`inputmode="none"`）を用意する方式だったが、**実装ではそもそも専用の入力欄を持たない**。「スキャナー」選択中のみ、画面全体の`keydown`イベントをグローバルに監視し、`input`/`textarea`/`select`等にフォーカスしている場合は無視する方式を採用した。スキャナーが送信する文字列をバッファに蓄積し、直前の入力から120ms以上間隔が空いたら新しい読み取りとしてリセット、Enter/Tabキーを検知した時点のバッファをシリアルコードとして確定する（150ms入力が無ければバッファを破棄）
- **事前準備（運用）**：社用iPhoneの「設定」→「Bluetooth」でスキャナーと事前ペアリング。iPhoneのキーボード言語を「英語（米国）」に設定（メーカー仕様）。画面内にはペアリング手順を表示しないため、ユーザーマニュアルを参照する運用とする
- **カメラとの切り替え**：当初案は「カメラボタン」と「Bluetooth入力欄」を同一画面に常時両方表示する方式だったが、2026-09の見直しにより画面上部のトグルボタンで「カメラ」「バーコード（スキャナー）」を明示的に切り替える方式に変更した。「バーコード」選択時のみ上記のキー入力監視が有効になる

### 5-1. カメラAPI実装方針

### ライブラリ選定（要確認）

iOSのSafariは `BarcodeDetector` APIの対応が不安定なため、ライブラリを使用する。

| ライブラリ | iOS Safari対応 | 備考 |
|-----------|---------------|------|
| `@zxing/browser` | ◎（iOS 14.3+） | WebRTC使用。**Code 128対応。採用決定** |
| `quagga2` | ○ | 旧Quaggaの後継。軽量 |
| `html5-qrcode` | ◎ | ラッパーライブラリ。導入が簡単 |

→ **`@zxing/browser` に決定**（バーコード種類：Code 128 確認済み。実機での動作確認は開発時に実施）

**実装メモ（2026-10-14、実装に合わせて修正）：** 当初案は本リポジトリにビルド構成が無いことを前提に、`@zxing/browser`をESモジュール形式のまま手動でベンダリングする方式を想定していた。実際には、このモバイル機能専用に`package.json`＋`esbuild`による簡易ビルドパイプラインが新設されており、`assets-src/barcode-scanner.js`（`@zxing/browser`をimportするソース）を`npm run build`で`src/public_html/public/assets/js/barcode-scanner.js`（IIFE形式・minify済みの単一ファイル）にバンドルする方式になっている。

### 読み取りフロー（JavaScript）

```
1. 「バーコードを読み取る」ボタン押下
        ↓
2. カメラ起動許可ダイアログ（初回のみiOSが表示）
        ↓
3. ハーフモーダル内でカメラプレビュー開始
        ↓
4. バーコード検出
    ├─ 新規シリアルコード → リストに追加 + 効果音/バイブ → カメラ継続
    └─ 重複シリアルコード → トースト「すでに読み取り済みです」→ カメラ継続
        ↓
5. 「閉じる」ボタン押下でモーダルを閉じ、実行ボタン押下へ
```

### 確認が必要な事項

- UDSで使用しているバーコードの種類（Code 128 / Code 39 / その他）
- iOSのSafariのカメラ許可設定（MDM管理端末のため制約がある可能性）
- AnyConnect VPN接続中のカメラAPIへの影響
- Bluetoothスキャナー（BC-BS801D-V2-CW）接続中に、AnyConnect VPN接続やMDM管理端末の制約でBluetooth自体が制限されないか
- Bluetoothスキャナーの送信モード設定（初期値「同期送信」でよいか、「非同期送信」に変更するか）

## 7. APIエンドポイント（2026-10-14、実装の実際のURL・形式に合わせて全面修正）

| メソッド | URL | 処理 |
|---------|-----|------|
| GET | `/mobile/branch/menu?branch_key=...` | M-01。`branch_key`をサーバー側で検証し、メニュー画面を返す |
| GET | `/mobile/branch/scan/store/scan?branch_key=...`（回収は`scan/return/scan`） | M-02/M-03。読み取り画面を返す |
| POST | `/mobile/branch/scan/store/validate?branch_key=...&format=json`（回収は`scan/return/validate`） | 読み取った1件のシリアルコードの存在・ステータスを検証するAPI（リストに追加する前に都度呼び出す） |
| POST | `/mobile/branch/scan/store/process?branch_key=...&format=json`（回収は`scan/return/process`） | 一括処理実行（JSON API） |
| GET | `/mobile/branch/error` | E-01 |

### POSTリクエスト（個別バリデーションAPI `.../validate`）

```
serial_cd  : 読み取った1件のシリアルコード
```

### レスポンス（個別バリデーションAPI）

```json
{
  "exists": true,
  "serial_cd": "ABC123456789",
  "message": ""
}
```

### POSTリクエスト（一括実行API `.../process`）

```
serial_cds[]  : {シリアルコード1}, {シリアルコード2}, ...
```

`branch_key`はURLクエリパラメータとして渡し、サーバー側で毎回`branch_cd`を再解決する（クライアントから`branch_cd`を直接送信させず、認可チェックの迂回を防止する）。

⚠️**サーバー側に`serial_cds[]`の件数上限チェックは実装されていない**（詳細は開発概要書参照）。

### レスポンス（一括実行API）

```json
{
  "success": false,
  "success_count": 2,
  "error_count": 1,
  "errors": [
    {
      "serial_cd": "XYZ112233445",
      "message": "端末が存在しません。"
    }
  ],
  "total_count": 3
}
```

当初案にあった`notice_count`/`notices[]`は実装されていない。キャンセル返却予定端末（`device_status_cd=18`）は他の対象外ステータスと同じく`errors[]`に含まれる。
