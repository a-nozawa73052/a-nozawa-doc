作成日: 2026-10-08
対象システム: UDS (uds-web)
依頼元チャット: https://chat.google.com/room/AAAATMyh0KQ/ZAFw2RV3Fao/ZAFw2RV3Fao?cls=10

## 1. 改修背景・目的

### 背景

センターの出荷画面で出庫処理を行うと、出荷CSV・送り状Excel（福山／SBS）・UNIS移動Excelの3ファイルが作られ、S3に保存されて `export_lists` に1ファイル1行で登録される。センター南港では1か月に約630回の出庫がある（2026年9月は629回、明細は12,981行）。依頼元は、このファイルを社内での確認・集計（シリアル・品名・出荷先・顧客情報の確認、品目ごとの台数集計、シリアル管理）に使うため、期間を指定してまとめて取得したいと考えている。

要望を調査する中で、既存の出庫処理に次の2つの障害が見つかった。

- **障害1：S3上のファイルが上書きされて消える**　ファイル名が秒までの日時（`YmdHis`）しか含まないため、同じ秒に出庫すると同じS3キーになり、後から出力したファイルが前のファイルを上書きする。2025/06〜2026/10の約1年4か月で14件発生している（同じ管轄の別ユーザー12件、別の管轄の別ユーザー1件、同じユーザー1件）。S3のバージョニングが無効なので、消えたファイルは復元できない。
- **障害2：同じ明細が二重に出庫される**　`action_download_save` は、対象をロックせずに読み込み、更新の条件にも「`complete_request_date` がまだ空」を入れていない。そのため、二重クリックや複数タブで2つのリクエストが同時に届くと、両方が出庫処理を行う。2026年9月の南港では、同じ16明細が2つのファイルに出力されていた。

### 課題

| 課題 | 内容 |
|-----|------|
| 期間でまとめて取得できない | 出力履歴画面では、自分が出力したファイルを1件ずつしかダウンロードできない。1か月分（約630ファイル）を手作業で結合する必要がある |
| S3上のファイルが上書きされる（障害1） | 同じ秒に出庫すると、出庫ファイルが消える。別の管轄のファイルに置き換わる場合もある |
| 二重出庫が起きる（障害2） | 同じ明細が2回出庫処理され、ファイルも2回出力される。端末ステータスも2回更新される |
| 出荷CSVの日付が実際の出荷日と違う | 出荷CSVの「組織間移動日」には出庫操作の日時（`complete_request_date`）が出ている。依頼元は、出荷画面で入力した出荷日（`shipping_date`）を出したい |

### 目的

- 期間とセンターを指定して、出荷CSVと送り状Excelを1回の操作でそれぞれ1ファイルとして取得できるようにする
- 出庫ファイルの上書き（障害1）と二重出庫（障害2）をなくす
- 出荷CSVの「組織間移動日」に出荷日（`shipping_date`）を出力する

## 3. 仕様

### 3-1. 期間一括DL画面

```
[ 履歴一覧 ] [ 期間一括DL ]  ← 出力履歴のサブナビゲーション
─────────────────────────────────────────────
 期間      [2026/09/01 📅] 〜 [2026/09/30 📅]   ※最大31日
           （初期値：前月の1日〜末日）

 センター  センター南港（0100080000_01）        ← センターのユーザー：表示のみ
           [ センター南港            ▼ ]          ← 管理者：選択式

 [ 出荷CSVをダウンロード ]  [ 送り状（福山）をダウンロード ]

 ・期間は出庫操作の日時（組織間移動完了日）で判定します
 ・送り状の住所・宛名は現在の契約情報で出力されます
 ・出庫後に削除された依頼は含まれません
─────────────────────────────────────────────
```

| 項目 | 仕様 |
|-----|------|
| 表示できるユーザー | 管理者（user_div=1）とセンター（user_div=2）のみ。権限は `mosauth.php` で付与し、画面に直接アクセスされても弾く |
| 期間 | From／To を日付で指定する（既存の `js-datepicker` を使う）。最大31日（依頼元確認済み）。初期値は前月の1日〜末日 |
| センター | センターのユーザーは自分の管轄（`jurisdiction_branch_cd`）に固定し、POSTされた値はサーバー側で上書きする。管理者は福山とSBSの対象センター（`define.php` の `fukuyama_shipment_center_list` と `sbs_shipment_center_list`）から選ぶ |
| 送り状ボタン | 選んだセンターに応じて「送り状（福山）」「送り状（SBS）」と表示を切り替える。どちらのリストにも入っていないセンターなら表示しない |
| 出力形式 | ZIPにせず、ボタンごとに1ファイルを返す |
| ファイル名 | `shipment_YYYYMMDD_YYYYMMDD.csv`、`fukuyama_YYYYMMDD_YYYYMMDD.xlsx`、`sbs_YYYYMMDD_YYYYMMDD.xlsx`（日付は指定した期間のFrom／To） |
| 入力チェック（サーバー側） | 期間が未入力、開始日が終了日より後、31日を超える、センターの指定が不正、該当する出庫がない。いずれも既存のエラーメッセージの仕組みで画面に表示する |
| 二度押しの防止 | ダウンロード中はボタンを押せないようにする |
| 出力履歴への登録 | 一括DLのファイルは `export_lists` に登録しない（S3にも保存しない） |

### 3-2. 対象の明細の取り方（方式B：DBから作り直す）

当時出力したS3のファイルは使わず、DBから作り直す。依頼元が、処理速度とサーバー負荷を考慮してこの方式を選んだ。

```sql
-- 対象の明細（出荷CSV・送り状で共通）
WHERE shipping_requests.deleted_at IS NULL           -- 出庫後に削除された依頼は含めない
  AND shipping_requests.request_type_cd IN (1, 2)    -- 通常新設・支店在庫
  AND shipping_requests.center_cd = :center_cd
  AND shipping_requests.complete_request_date >= :from          -- From 00:00:00
  AND shipping_requests.complete_request_date <  :to + 1日      -- To の翌日 00:00:00
```

- 期間は出庫操作の日時（`complete_request_date`）で判定する。インデックス（`idx_ship_req_complete_request_date`）がある。
- センターは `shipping_requests.center_cd` で絞る。2026年9月の出庫で、南港・IoT PLATFORM・北海道の3センターとも、出力したユーザーの管轄と完全に一致することを確認した。
- 今の出庫処理にある「端末ステータスが4,5」という条件は付けない（出庫後はステータスが変わっているため）。
- 2026年9月の南港で試算すると、作り直した結果は12,965行・628回で、当時の出力（12,981行・629回）との差は二重出庫の16行・1回分だけだった。

### 3-3. 出荷CSV（一括）

- 列は毎日の出荷CSVと同じ（`csv_formats` の div=23、15列）。文字コードは cp932。
- 並び順は `complete_request_date` の昇順、その中は既存の並び順に従う。

### 3-4. 送り状（一括）

- 列は毎日の送り状と同じ（福山31列、SBS25列）。
- まとめ方は「出庫処理ごと×顧客で1行」とする（依頼元確認済み）。日々の送り状を期間分並べたのと同じ形になる。
- 今の送り状は、1回の出庫の中で同じ顧客宛ての端末を1行にまとめている。一括でも同じ形にするため、**まとめる単位に `complete_request_date`（出庫処理ごと）を加える**。

| 区分 | 今のまとめ方 | 一括のまとめ方 |
|-----|------------|--------------|
| 通常新設・直送 | `unis_customer_cd` | `complete_request_date` ＋ `unis_customer_cd` |
| 支店在庫 | `request_branch_cd` | `complete_request_date` ＋ `request_branch_cd` |

- 今の処理は、明細1件ごとに `Model_Direct_Shipment::get_shipment_type_cd_by_shipping_request_id` と `Model_Shipping_Request::get_request_type_cd` を呼んでいる。1か月分（約13,000件）では約26,000回の問い合わせになるため、一括用には直送区分と依頼種別を JOIN でまとめて取得する。
- 住所・宛名・電話番号は、今の契約情報（`contracts`、`branch_replacement`）で出力する。依頼元は、顧客CD（S_品名記事２）で顧客を特定できればよいとしている。

### 3-5. 出荷CSVの「組織間移動日」を出荷日にする

毎日の出荷CSVと一括DLの両方に適用する。列の見出し名は「組織間移動日」のまま変えない。

| 対象 | 変更内容 |
|-----|---------|
| `csv_formats`（DBのデータ） | div=23 の行のキーを `complete_request_date` から `shipping_date` に変える |
| `Download_Csv_Center_Shipment` | `get_data` で `shipping_requests.shipping_date` を取得し、`modifier` でキー `shipping_date` を `Y/m/d` 形式で出力する |
| `Download_Csv_Center_Shipment2`（IoT PLATFORMの新規端末一括登録CSV） | 同じ列定義（div=23）を使っているので、`modifier` の判定キーを `shipping_date` に変える。出力内容（出力した日の日付）は変えない |

DBのデータ変更（リリース時に各環境で実行する。実行前に必ず確認を取る）：

```sql
-- 実行前の確認
SELECT id, `div`, `key`, name, sort FROM csv_formats
WHERE `div` = 23 AND `key` = 'complete_request_date';

-- 変更
UPDATE csv_formats
SET `key` = 'shipping_date', updated_at = NOW()
WHERE `div` = 23 AND `key` = 'complete_request_date';
```

- 環境ごとにidが違う可能性があるので、idではなく `div` と `key` で指定する。
- コードとデータのどちらを先にリリースしても出力が空にならないよう、移行期間中は `modifier` で `complete_request_date` と `shipping_date` の両方のキーを受け付ける。データ変更が全環境で終わったら、古いキーの分岐を消す。

### 3-6. 出庫ファイル名を重複しない形にする（障害1の対策）

| ファイル | 変更前 | 変更後 |
|---------|-------|-------|
| 出荷CSV | `20260312145249.csv` | `20260312145249_22_123.csv` |
| 送り状（福山） | `fukuyama_20260312145249.xlsx` | `fukuyama_20260312145249_22_123.xlsx` |
| 送り状（SBS） | `sbs_20260312145249.xlsx` | `sbs_20260312145249_22_123.xlsx` |
| UNIS移動 | `unis_20260312145249.xlsx` | `unis_20260312145249_22_123.xlsx` |
| ZIP（サーバーの一時ファイル） | `shipments_20260312145249.zip` | `shipments_20260312145249_22_123.zip` |

- 後ろに付ける値は `_<ログインユーザーのID>_<ミリ秒3桁>`。ユーザーIDで別ユーザーとの衝突を、ミリ秒で同じユーザーの同時実行との衝突を防ぐ。
- 日時は出庫処理1回につき1度だけ決め、全ファイルで同じ値を使う（今は各クラスがそれぞれ現在時刻を取っていて、1秒ずれることがある）。
- ZIPはサーバー上の一時ファイルも同じ名前になるため、同時実行で壊れないよう同じ規則にする。

### 3-7. 二重出庫を防ぐ（障害2の対策）

- `update_shipping_requests` の更新条件に `shipping_requests.complete_request_date IS NULL` を加える。
- 更新できた件数が選択した件数と違う場合は、ロールバックして「他の操作で出庫済みの明細が含まれています。画面を更新してから再度実行してください」と表示する。`update_shipping_requests` は端末ステータスの更新とファイル生成より前に実行されるので、この時点で止めればそれ以降の処理は動かない。
- 画面側では、出庫ボタンを1回押したら押せないようにする（補助的な対策）。

## 4. 変更前後フロー比較

### 変更前

```
【期間でまとめて取得する】
出力履歴画面（自分の出力分のみ）
  → 1ファイルずつダウンロード（1か月で約630回）
  → 手作業で結合

【出庫処理】
出荷画面で出庫ボタン
  → 対象を読み込む（complete_request_date が空のもの）※ロックなし
  → complete_request_date を書き込む ※「まだ空」の条件なし → 同時実行で二重出庫
  → 端末ステータスを更新
  → 3ファイルを生成（ファイル名 YmdHis、クラスごとに時刻を取得）
  → S3にアップロード ※同じ秒だと上書き
  → export_lists に登録 → ZIPを返す
```

### 変更後

```
【期間でまとめて取得する】
出力履歴 ＞ 期間一括DL タブ（admin／center のみ）
  → 期間（最大31日）とセンターを指定
  → [出荷CSV] shipping_requests を center_cd ＋ complete_request_date で抽出
             → shipment_YYYYMMDD_YYYYMMDD.csv を返す
  → [送り状]  同じ条件で抽出し、出庫処理ごと×顧客でまとめる
             → fukuyama_／sbs_YYYYMMDD_YYYYMMDD.xlsx を返す

【出庫処理】
出荷画面で出庫ボタン（押したら押せなくなる）
  → 対象を読み込む
  → complete_request_date を書き込む（条件：まだ空）
       → 更新件数が選択件数と違えばロールバックしてエラー表示
  → 端末ステータスを更新
  → 日時を1度だけ決め、3ファイルを生成（YmdHis_<user_id>_<ミリ秒>）
  → S3にアップロード（キーが重複しない）
  → export_lists に登録 → ZIPを返す
```

## 6. 影響範囲・リスク

- **他システムへの影響**：なし（UDSの画面とDBの中で完結する）。
- **毎日の出荷CSVへの影響**：
  - 「組織間移動日」の中身が、出庫操作の日時から出荷日に変わる。見出し名は変わらないので、利用者に事前に周知する。
  - ファイル名の形式が変わる（`_<user_id>_<ミリ秒>` が付く）。
- **IoT PLATFORMの新規端末一括登録CSV**：同じ列定義（div=23）を使っているので、`modifier` の判定キーを合わせて変える。出力内容は変わらない。
- **送り状の内容**：一括の送り状の住所・宛名は今の契約情報で出力されるので、当時渡した送り状と違う場合がある。依頼元は了承済み。
- **期間の基準の違い**：一括DLの期間は出庫操作の日時で判定するが、出荷CSVに出るのは出荷日。両者がずれている明細は、CSVの日付が期間の外に見えることがある。画面に注意書きを出す。
- **リリースの手順**：
  - `csv_formats` のデータ変更は、各環境（dev／stg／prd）でコードのリリースと同じタイミングに実行する。移行期間中は両方のキーを受け付けるので、順番がずれても出力は空にならない。
  - データ変更は取り消しにくいので、実行前に対象の行を確認する。
- **既存データの扱い**：上書きで消えた過去のファイルは復元できない（バージョニングが無効）。一括DLはDBから作り直すので、過去分も期間を指定すれば取得できる。
- **別件として扱うもの**：出力履歴のダウンロード（`action_download_csv`／`Model_Export_Lists::get_file_name_by_id`）は、出力者が本人かを確認していない。idを直接POSTすると他人のファイルを取得できる。本改修の範囲外とし、別のチケットで対応する。
