# 対応書 — 旧IPv4アドレス解約対応（既存 delete_batch フロー利用）

**作成日:** 2026-08-25
**種別:** 一度切りの手動対応（コード改修・AWSリソース新規作成は行わない）
**対象システム:** UDS ⇔ アルテリア・ネットワークス vLinkサービス（BoostAES G3）

> 前回検討していた「専用一時Lambdaを新規作成する方式」は不採用とし、既存の
> `batch_request_arteria_api`（Lambda, 変更なし）が既に持つ `delete_batch` 処理を
> そのまま利用する方式に変更した。背景・API仕様の詳細は `改修概要.md` を参照。

---

## 1. 対応概要

対象の旧IPv4アカウントを `pppoe_request_contracts` テーブルに `request_type='delete'` として登録し、
既存Lambda（`stg-batch_request_arteria_api` / `prd-batch_request_arteria_api`、新規作成・コード変更なし）を
`{"request_type": "delete_batch"}` で手動invokeすることで、アルテリアvLink `AccountUpdateService`
（status:2＝クローズ）による解約を実行する。

## 3. 対応手順

### 3-1. 事前チェック（必須・データINSERT前に実施）

対象データをINSERTする前に、テーブル内に**他の未処理レコードが残っていないか**を確認する。

```sql
SELECT * FROM pppoe_request_contracts
WHERE deleted_at IS NULL
  AND request_type IN ('delete', 'so_cancel', 'so_v4_cancel');
```

- 意図しないレコードが見つかった場合、それらも一緒に処理されてしまう旨を関係者に共有し、実行タイミングを調整する（急ぎでなければ問題ないことが多いが、事前共有は必須）。

### 3-2. 対象データのDB登録（`uds-sql-support`フローに準拠）

1. `main`ブランチから`fix/yyyymmdd`ブランチを作成
2. `uds-sql-support/yyyymmdd/pppoe_request_contracts/` 配下に以下を作成
   - `README.md`：依頼内容（対象契約CD・シリアルCD一覧、依頼者、依頼日時）
   - `execution.sql`：対象データのINSERT文（`request_type='delete'`、`created_at`を当月初日より前の日付で明示指定）
3. mainブランチへのMR作成 → レビュー・承認
4. 承認後、検証環境（stg）→本番環境（prd）の順でSQLを実行

**execution.sql イメージ**（`created_at`を過去日付に指定する点が通常の`insertRecord`処理と異なる）:

```sql
INSERT INTO pppoe_request_contracts
    (request_type, contract_cd, serial_cd, customer_state_name, ngn_common_id, created_at, updated_at)
VALUES
    ('delete', '<contract_cd>', '<serial_cd>', '<customer_state_name>', NULL, '<当月初日より前の日付>', NOW());
```

### 3-3. 検証環境での疎通確認

1. stg環境のDBにダミー相当データがINSERT済みであることを確認
2. `stg-batch_request_arteria_api`（既存Lambda）を以下のペイロードでinvoke

   ```bash
   aws lambda invoke --function-name stg-batch_request_arteria_api \
     --payload '{"Records":[{"body":"{\"request_type\":\"delete_batch\"}"}]}' \
     response.json
   ```

3. CloudWatch Logsでエラーの有無を確認（検証環境には実顧客アカウントが存在しないため、ここでの確認は疎通・認証・レスポンス解析までにとどまる）

### 3-4. 本番実行前の事前確認（読み取り専用）

「5.PPPアカウント情報検索」または「9.PPPアカウント情報詳細」で、本番環境の対象アカウントが実在するか・現在のステータス（アクティブ等）を確認する。副作用のない照会のみ。

### 3-5. 本番実行

1. 本番DBへ`execution.sql`を実行（3-2のフローに沿って承認済みのもの）
2. `prd-batch_request_arteria_api`（既存Lambda）を以下のペイロードでinvoke

   ```bash
   aws lambda invoke --function-name prd-batch_request_arteria_api \
     --payload '{"Records":[{"body":"{\"request_type\":\"delete_batch\"}"}]}' \
     response.json
   ```

### 3-6. 結果確認

- `pppoe_request_contracts`テーブルで対象行の`deleted_at`が更新されていることを確認
- CloudWatch Logsでエラー通知（Google Chat Webhook）が飛んでいないか確認
- 「9.PPPアカウント情報詳細」で対象アカウントの`status`が`2`（クローズ）になっていることを確認

## 4. リスク・注意事項

- **無条件一括処理**：`delete_batch`は対象を絞れないため、想定外のレコードが同時に処理される可能性がある。3-1の事前チェックを必ず実施すること。
- **不可逆操作**：解約実行後の取り消しはできない。3-4の事前確認を徹底すること。
- **タイムアウト**：対象件数が多い場合、300秒制限に注意。必要であれば対象を分割して複数回invokeする。
- **命名規則の不一致リスク**：旧IPv4の`serviceAcctId`が現行ロジックの組み立て結果と一致しない場合、エラーコード`3104`（指定されたアカウント情報の取得に失敗）等になる可能性がある。可能な限り実際の`service_acct_id`を事前入手し、INSERT時に活用できるようスキーマ拡張が必要か確認する（※現状の`pppoe_request_contracts`には`service_acct_id`カラムが無いため、`contract_cd`＋`serial_cd`からの組み立てに頼らざるを得ない点は既知の制約）。
