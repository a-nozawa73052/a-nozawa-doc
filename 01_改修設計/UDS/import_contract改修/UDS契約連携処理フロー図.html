図1

import_contract — 契約取り込み処理（旧方式）

NeOSが契約TSVをS3にPUTするたびに起動するイベント駆動型Lambda。契約の新規／更新を判定し、UDSの各テーブルへ反映しつつ、同一ファイルをSGS向けバケットへそのままコピーする。

%%{init: {'theme':'default'}}%%
flowchart TD
    NeOS["NeOS"] -->|"contract_yyyymmddhhiiss.tsv を PUT"| S3in[("S3: udsapi-contract")]
    S3in -->|"S3イベント通知"| L1["Lambda: import_contract（旧）"]
    L1 -->|"元ファイルをそのままコピー"| S3sgs[("S3: prd2-sgs-import/contract")]
    L1 --> Parse["TSV読込・改行分割・列数チェック(53列)"]
    Parse --> Validate{"必須/文字数/日時形式
バリデーション"}
    Validate -->|"NG行"| ErrFlag["hasError = true
(該当行はスキップ)"]
    Validate -->|"OK行"| Lookup["device_types / branch_replacement /
unis_customer_brands を参照"]
    Lookup --> Exist{"contracts に
contract_cd が存在?"}
    Exist -->|"新規"| Insert["contracts へ INSERT
shipping_requests へ INSERT
direct_shipments へ INSERT
contract_bgms 等の紐付け"]
    Exist -->|"既存"| Update["contracts を UPDATE
updateUdsStatus()"]
    Insert --> CPM(["CPM通知API"])
    Insert --> UX(["UX SQS"])
    Update --> UX
    Insert --> Finally["finally: DB接続クローズ"]
    Update --> Finally
    Finally -->|"hasError あり"| S3err[("S3: error/")]
    Finally -->|"正常終了"| S3done[("S3: done/")]

    classDef store fill:#e4eafc,stroke:#2f5fd1,color:#1b2330;
    classDef lambda fill:#2f5fd1,stroke:#2f5fd1,color:#ffffff;
    classDef ext fill:#ffffff,stroke:#8b93a1,color:#1b2330,stroke-dasharray: 3 3;
    class S3in,S3sgs,S3err,S3done store;
    class L1 lambda;
    class CPM,UX ext;

図2

import_neos_uairplan — 契約更新パイプライン（先行事例）

UNIS発のTSVを2段のLambdaで処理する更新専用パイプライン。ワークテーブルを介した1行単位トランザクション＋失敗行を残す再試行設計で、import_contract新方式の設計元になった。

%%{init: {'theme':'default'}}%%
flowchart TD
    UNIS["UNIS"] -->|"neos_uairplan_*.tsv を PUT"| S3ready[("S3")]
    S3ready -->|"S3イベント通知"| L2["Lambda:
preprocess-neos-uairplan-tsv"]
    L2 -->|"生ファイルを全件コピー"| S3sgs2[("S3: prd2-sgs-import/neos_uairplan")]
    L2 --> Filter{"uds.contracts に
contract_cd が存在?
(1000行ずつ突合)"}
    Filter -->|"一致行のみ INSERT"| Work[("uds.work_imported_neos_uairplan")]
    Work -->|"id ASC, LIMIT 1000
でポーリング"| L3["Lambda: import_neos_uairplan"]
    L3 --> Exist2{"contracts に
contract_cd が存在?
(1行単位トランザクション)"}
    Exist2 -->|"なし"| Notify1(["Google Chat通知
(行は削除せず残す)"])
    Exist2 -->|"あり"| Upd["contracts UPDATE(品目・service_cd)
contract_com_devices / contract_mdm_devices
contract_uphone_locations (Geocoding)
serials / direct_shipments
contract_mdm2_devices"]
    Upd --> Arteria(["SQS: Arteria連携キュー"])
    Upd -->|"成功"| Delete["work_imported_neos_uairplan
から DELETE"]
    Delete -->|"全ラウンド完了後
まとめて実行"| UX2(["UX SQS"])
    Upd -->|"失敗(rollback)"| Notify2(["Google Chat通知
行は削除せず次回再試行"])

    classDef default fill:#ffffff,stroke:#5b6472,color:#1b2330;
    classDef store fill:#e4eafc,stroke:#2f5fd1,color:#1b2330;
    classDef lambda fill:#2f5fd1,stroke:#2f5fd1,color:#ffffff;
    classDef ext fill:#ffffff,stroke:#8b93a1,color:#1b2330,stroke-dasharray: 3 3;
    class S3ready,S3sgs2,Work store;
    class L2,L3 lambda;
    class Notify1,Notify2,Arteria,UX2 ext;

contract.tsv の到着から最終処理まで（GitLab MR #211 / GitHub PR #3 実装ベース）

flowchart TD

未確定事項（要ACE側・事業部確認） — UDS側の基本方針は「ACE統合後もSGS・GRS・UMへの影響を最小化する」こと。現時点で確定していないのは主に以下の3点。
  • neos_item_pac_cd 廃止に伴う直送センター振分・SSID自動設定ロジックへの影響
  • u2データ廃止のタイミングと、SGSへの移行方法
  • NeOS/UNISとACEの並用期間中のS3パス設計・二重処理防止策
