## 0001. preprocess → work テーブル → import Lambda の非同期アーキテクチャ採用

- ステータス: 承認
- 日付: 2026-09-11
- 対象システム・機能: UDS / import_contract Lambda
- 決定者: a-nozawa

### コンテキスト

現行の `import_contract` は S3 PUT トリガーで起動し、TSV ファイルを1行ずつ同期処理する。行数・外部API（CPM通知API / UX SQS）の処理時間次第で Timeout 900秒に近づくリスクがある。同様の問題を `import_neos_uairplan` で解決した「work テーブル経由の非同期処理」を適用するかどうかを判断する必要があった。

### 検討した代替案

#### 案A: 現行アーキテクチャ維持（S3 トリガー直接処理）
- 内容: 現行のまま S3 PUT トリガーで全行同期処理。Timeout 値を引き上げて対応。
- メリット: 変更なし。実装コストゼロ。
- デメリット: 根本的なタイムアウトリスクが残る。行数増加に対してスケールしない。複数ファイル同時投入時の並列起動リスクも残る。

#### 案B: work テーブル経由の非同期処理（import_neos_uairplan 準拠）
- 内容: preprocess Lambda（S3トリガー）が work テーブルに INSERT し、import Lambda（EventBridge 10分）が 1000件ずつ処理。
- メリット: 1実行あたりの処理件数が上限付きになりタイムアウトリスクがなくなる。ラウンドロビンで同一 contract_cd の滞留が他の処理をブロックしない。import_neos_uairplan と運用パターンが統一される。
- デメリット: preprocess Lambda の新規作成が必要。work テーブルの DDL 作成が必要。S3 イベント通知の切り替え作業が必要。

### 決定

**案B（work テーブル経由の非同期処理）を採用**。

タイムアウトリスクの排除と import_neos_uairplan との運用統一を優先する。実装コストは preprocess 新規作成と import 改修で発生するが、`import_neos_uairplan` のコードを参考にすることで工数を抑えられる。

### 影響・トレードオフ

- 性能・データ量急増時: 10分 × 1000件 が処理上限。ピーク時に大量滞留すると解消が遅れる。CloudWatch で未処理件数の監視が必要。
- 他システムへの影響: SGS（ファイルコピー先は変わらない）、CPM・UX SQS（import 側で引き続き呼び出す）
- 運用・保守への影響: work テーブルの監視が追加される。デバッグは work テーブルを参照することで途中状態が確認できるようになる（現行より改善）。
- 今後変更する場合の制約: work テーブルへの滞留量増加に合わせて LIMIT 値や EventBridge 実行頻度の調整が必要。

### 関連

- 関連ドキュメント: `改修概要書.md`（同フォルダ）
- 参考実装: `a-nozawa-doc/01_改修設計/UDS/import_neos_uairplan改修/`

## 0002. preprocess 側で device_types マスタ存在チェックを行い、存在する行のみ work テーブルへ INSERT

- ステータス: 承認
- 日付: 2026-09-11
- 対象システム・機能: UDS / preprocess-contract-tsv Lambda
- 決定者: a-nozawa

### コンテキスト

`device_types` マスタに存在しない `neos_item_cd` の行は、import Lambda 側でも処理できない（`getServiceCdInfo` が空を返し `continue` でスキップされる）。preprocess 側で事前にフィルタすることで import Lambda の不要な処理を削減できる。一方、import_neos_uairplan の preprocess では `contracts` 存在チェックを行っている。import_contract にも同様のプリフィルタを設けるかを判断する必要があった。

### 検討した代替案

#### 案A: preprocess では全行 work へ INSERT（フィルタなし）
- 内容: バリデーション（列数/NULL）のみ行い、device_types チェックは import 側に委ねる。
- メリット: preprocess がシンプル（UDS DB アクセスなし）。
- デメリット: import 側で device_types に存在しない行が1000件の枠を消費する。滞留が増えると解消が遅延する。

#### 案B: preprocess で device_types の neos_item_cd バルクSELECT → 存在する行のみ INSERT
- 内容: TSV の `neos_item_cd`（index 5）を収集してバルクSELECT し、device_types に存在する行のみ work へ INSERT。存在しない行はログ出力してスキップ。
- メリット: import 側の無駄な処理を排除。work テーブルに不要な行が溜まらない。
- デメリット: preprocess が UDS DB に接続する必要がある（バルク SELECT のみ）。

### 決定

**案B（preprocess で device_types バルクSELECT）を採用**。

import_neos_uairplan で preprocess が `contracts` 存在チェックを行うのと同じ設計方針。バルク SELECT のため DB 負荷は小さく、preprocess の役割として自然。

### 影響・トレードオフ

- preprocess Lambda が UDS DB 接続を持つ（import_neos_uairplan の preprocess と同じ構成）。
- device_types に新商材が追加されるまでの間、新商材の TSV 行は work へ入らないため手動対応が必要になる可能性がある。
- 今後変更する場合の制約: device_types マスタのメンテナンスが preprocess の動作に直結するため、マスタ変更時は注意が必要。

### 関連

- 関連ドキュメント: `改修概要書.md`（同フォルダ）

## 0003. CPM 通知 API の重複呼び出しを許容する

- ステータス: 廃止（後継: 0009）
- 日付: 2026-09-11
- 対象システム・機能: UDS / import_contract Lambda（CPM 通知 API 呼び出し）
- 決定者: a-nozawa

### コンテキスト

import Lambda が `contracts INSERT → CPM API 呼び出し → work DELETE` の途中でクラッシュした場合、次回 EventBridge トリガーで同じ work 行を再処理する際に CPM API が重複呼び出しされる可能性がある。CPM 側に冪等性がないため、重複通知がシステム上どのような影響を持つか確認したうえで対策を検討する必要があった。

### 検討した代替案

#### 案A: work テーブルに `cpm_notified_at` カラムを追加し、送信済みフラグで重複防止
- 内容: CPM API 呼び出し成功後に `cpm_notified_at` を UPDATE。次回リトライ時に NULL でなければスキップ。
- メリット: CPM の重複通知を確実に防止できる。
- デメリット: work テーブルのカラム追加と、import Lambda の UPDATE ロジック追加が必要。実装コストが増加する。

#### 案B: 重複呼び出しを許容（対策なし）
- 内容: Lambda クラッシュは稀なケースであり、CPM 側への影響は限定的と判断して許容する。
- メリット: 実装がシンプル。追加のカラム・ロジックが不要。
- デメリット: 重複通知が発生した場合は手動対応が必要。

### 決定

**案B（重複呼び出しを許容）を採用**。

Lambda クラッシュ（CPM API 呼び出し後・work DELETE 前）という稀なケースであり、運用上許容できる範囲と判断した。問題が顕在化した場合は `cpm_notified_at` カラムを追加する案Aに移行する。

### 影響・トレードオフ

- Lambda クラッシュ時に CPM へ重複通知が発生する可能性がある。
- CPM 側でのデータ確認・手動修正が必要になるケースがある。
- 今後変更する場合: `work_imported_contract` に `cpm_notified_at DATETIME DEFAULT NULL` カラムを追加し、import Lambda で送信済みチェックを行うことで対応可能。

### 関連

- 関連ドキュメント: `改修概要書.md`（同フォルダ）

## 0004. トランザクション制御を復活させ、1行1トランザクションで処理する

- ステータス: 承認
- 日付: 2026-09-11
- 対象システム・機能: UDS / import_contract Lambda
- 決定者: a-nozawa

### コンテキスト

現行の `import_contract` では `beginTransaction` / `commit` / `rollback` がコメントアウトされており、トランザクション制御がない。work テーブル方式に移行することで「1行ずつ独立して処理する」アーキテクチャになるため、トランザクションを復活させる機会として位置づける。

### 検討した代替案

#### 案A: トランザクション制御なし（現行踏襲）
- 内容: コメントアウトのままにし、トランザクションを設けない。
- メリット: 変更最小限。
- デメリット: contracts INSERT 成功後に shipping_requests INSERT でエラーが発生した場合、contracts だけ存在する不整合状態が残る。

#### 案B: 1行 1トランザクション（beginTransaction / commit / rollback を復活）
- 内容: ラウンドロビンの各行の処理を1つのトランザクションで囲む。エラー時は rollback。
- メリット: DB の整合性が保たれる。部分コミットを防止できる。
- デメリット: トランザクション中にエラーが発生した場合、work 行は削除されず次回リトライで再処理される（冪等性の設計が必要）。

### 決定

**案B（1行 1トランザクション）を採用**。

work テーブル方式によりリトライが自然に行われる設計になるため、トランザクションを復活させてもリトライ時の冪等性が `isExistData` の分岐と既存の重複チェックで担保される。

### 影響・トレードオフ

- rollback 後に同じ work 行が次回 EventBridge で再処理される（リトライ設計として意図的）。
- `contracts` の `contract_cd` UNIQUE 制約と `direct_shipments` の重複チェックにより、contracts INSERT の冪等性は担保される（既存コード）。
- 今後変更する場合の制約: UNIS DB への書き込み（`updateUnisCustomerServiceGroups`）はトランザクションに含まれないため、UDS トランザクションが rollback されても UNIS 側の変更は戻らない点に注意。

### 関連

- 関連ドキュメント: `改修概要書.md`（同フォルダ）

## 0005. UX SQS の重複排除キーを contract_cd ベースに変更する案は採用しない

- ステータス: 廃止（後継: 0009）
- 日付: 2026-10-02
- 対象システム・機能: UDS / import_contract Lambda（UX SQS 送信、`import_ux.js`）
- 決定者: a-nozawa

### コンテキスト

GitLab MR #211 のPRコメントに「`MessageDeduplicationId` をタイムスタンプから `contract_cd` ベースに変更し、連携失敗→ロールバック→再処理時の重複送信を防ぐ」という対応が記載されていた。しかし `develop` との差分を確認したところ `import_ux.js` には変更が反映されておらず、コードは `String(moment().valueOf())` のままだった。この対応自体を実装すべきかどうかをレビューの中で検討した。

0003で「CPM通知APIの重複呼び出しは許容する」と決定済みだが、UX SQS側はPRコメントで対策が試みられていたため、その対策の妥当性を個別に評価する必要があった。

### 検討した代替案

#### 案A: `MessageDeduplicationId` を `contract_cd` ベースに変更する（PRコメント記載の対応）
- 内容: 重複排除キーを `contract_cd` の値にする。
- メリット: 実装が1行で済む。
- デメリット: SQS FIFOの重複排除ウィンドウは5分間固定だが、本バッチの再試行間隔（EventBridge 10分）はそれより長いため、ロールバック後の再処理時の重複送信を防ぐという本来の目的を達成できない。さらに、ラウンドロビン処理により同一 `contract_cd` に対する複数の正当な更新が同一実行内の別ラウンドで5分以内に処理された場合、後続の正当な通知がSQS側で誤って重複排除され欠落する新たなリスクを生む。

#### 案B: 現状維持（タイムスタンプベース。重複排除は実質機能しない）
- 内容: `MessageDeduplicationId` を変更しない。
- メリット: 変更不要。正当な更新の取りこぼしは発生しない。
- デメリット: ロールバック後の再処理時にUX通知が重複送信される可能性は残る（0003のCPM重複許容と同種のリスク）。

#### 案C: `ux.send()` の呼び出しタイミングを、全ラウンド処理完了後（コミット確定後）にまとめて実行する設計に変更する（`import_neos_uairplan` 方式）
- 内容: 現行コードはトランザクション末尾・コミット直前で都度 `ux.send()` を呼んでいるが、これを全行の処理が終わった後にまとめて実行する方式に変更する。
- メリット: 一度コミットされた行は二度と再試行されないため、通知も構造的に一度きりになり、重複送信の根本原因を解消できる。
- デメリット: 現行実装からの設計変更が必要で、実装コストが発生する。

### 決定

**案B（現状維持）を採用**。`contract_cd` ベースへの変更（案A）は実施しない。

案Aは本来の目的（ロールバック後の重複送信防止）を達成できないばかりか、正当な通知の欠落という新たなリスクを生むため却下。案Cが構造的には望ましいが、今回のMRのスコープでは見送り、0003と同様に「重複通知を許容する」方針を踏襲する。

### 影響・トレードオフ

- 性能・データ量急増時への影響: 特になし。
- 他システムへの影響: ロールバック→再処理時にUX側へ重複送信が発生し得る。実害の有無はUX側のSQS受信処理が「契約CDを受け取って最新状態を再同期する」冪等な設計になっているかに依存する。TODO: 要確認 — UX側の受信処理の冪等性。
- 運用・保守への影響: 重複送信が実害として顕在化した場合、案C（`ux.send()` のコミット後まとめ実行への変更）への移行を検討する。
- 今後変更する場合の制約: SQSの重複排除ウィンドウは5分固定でありSQS側の設定では延長できないため、重複排除キーの工夫では本質的に解決できない。対応するなら呼び出しタイミング自体の変更が必須。

### 関連

- 関連Issue/PR: GitLab `import_contract` MR #211
- 関連ドキュメント: `改修概要書.md`（同フォルダ）、ADR 0003（CPM通知APIの重複呼び出し許容）

## 0006. contract_cd のバリデーション文字数上限は21文字のまま維持する

- ステータス: 承認
- 日付: 2026-10-02
- 対象システム・機能: UDS / import_contract Lambda（`COLUMN_LIST[0]` バリデーション）
- 決定者: a-nozawa

### コンテキスト

改修概要書記載の `work_imported_contract` DDLでは `contract_cd VARCHAR(25) NOT NULL` と定義されており、本番 `contracts` テーブルの実カラム定義も `varchar(25)` だった。一方、`import_contract/index.js` の既存バリデーションロジック（`COLUMN_LIST[0].length`、今回のMRでは変更されていない）は `'21'` のままであり、レビュー時に桁数の不一致に見えたため、意図的な設計か確認した。

### 検討した代替案

#### 案A: バリデーション上限をDB定義に合わせて25に変更する
- 内容: `COLUMN_LIST[0].length` を `'25'` に変更する。
- メリット: DBのカラム定義と完全に一致する。
- デメリット: 契約コードの業務上の正式な最大長（21文字）より緩い制限になり、本来弾くべき不正な桁数のデータを通してしまう可能性がある。

#### 案B: バリデーション上限を21のまま維持する
- 内容: 変更しない。
- メリット: 契約コードの業務ルール（最大21文字）をそのまま維持できる。
- デメリット: DBのカラム定義（25文字）とアプリケーションのバリデーション上限（21文字）が一致せず、一見すると不整合に見える。

### 決定

**案B（21文字のまま維持）を採用**。契約コードの業務上の正式な最大長は21文字であり、DB列の25文字はそれより余裕を持たせた定義（データ型としての箱）である。バリデーションは業務ルール通り21文字を上限とするのが正しい。

### 影響・トレードオフ

- 性能・データ量急増時への影響: なし。
- 他システムへの影響: なし。
- 運用・保守への影響: DBカラム長とアプリケーションバリデーション長が異なる理由が分かりにくいため、本ADRおよびコード側にその旨のコメントを残すことが望ましい。
- 今後変更する場合の制約: 契約コードの業務ルール（最大21文字）が変わらない限り、`COLUMN_LIST[0].length` を変更する必要はない。

### 関連

- 関連ドキュメント: `改修概要書.md`（同フォルダ）

## 0007. Lambda 多重起動対策は Timeout 調整のみとし、ReservedConcurrentExecutions は設定しない

- ステータス: 提案中（TODO: 要確認あり）
- 日付: 2026-10-02
- 対象システム・機能: UDS / import_contract Lambda
- 決定者: a-nozawa

### コンテキスト

プレモータムレビューで、`work_imported_contract` に対する行ロック・ステータス管理が無いまま EventBridge によるポーリング型バッチにしたため、スケジュール起動が重なった場合に複数のLambda実行が同一work行を同時に処理し、`contracts` への重複INSERTや外部通知（CPM/UX）の重複実行が発生しうるリスクを指摘した。対策の方向性を検討した。

### 検討した代替案

#### 案A: `ReservedConcurrentExecutions: 1` を設定する
- 内容: Lambdaの同時実行数を1に制限する。
- メリット: 同一関数の同時実行を確実に1つに制限でき、多重起動による重複処理を構造的に防げる。EventBridgeからの呼び出しは非同期実行のため、スロットリングされた呼び出しはLambda側のリトライ機構で後から再試行される（消失しない）。
- デメリット: デプロイ設定の追加変更が必要。

#### 案B: Lambda の Timeout を 600秒（スケジュール間隔と同じ）に設定する
- 内容: 現行 900秒のTimeoutを600秒に短縮する。
- メリット: 詰まった実行を10分のスケジュール間隔内で確実に終了させられる。
- デメリット: スケジュール発火自体を制御するものではないため、多重起動の可能性を完全には排除できない（実行時間が599秒など境界に近い場合、次のスケジュール発火と重なる瞬間が残る）。CPM API等の外部呼び出しが遅延した場合、1000件の処理が600秒で終わらずTimeoutでKillされる頻度が増え、滞留が悪化する可能性もある（レビュー時に指摘済み）。

### 決定

**案B（Timeout 600秒への変更）を設定する方向**。ただし、Timeoutだけでは多重起動を完全には防げない点をレビューで指摘済みであり、その上でなお案Bのみで進めるか、案Aも追加するかについて、会話内で明示的な最終合意は確認できていない。

### 影響・トレードオフ

- 性能・データ量急増時への影響: TODO: 要確認（CPM API等の外部連携が遅延した場合、600秒Timeoutでは1000件を処理しきれない可能性がある）。
- 他システムへの影響: 多重起動が実際に発生した場合、`contracts`・`shipping_requests`・`direct_shipments` への重複INSERT、CPM/UXへの重複通知が起きうる（プレモータムレビュー参照）。
- 運用・保守への影響: TODO: 要確認。
- 今後変更する場合の制約: TODO: 要確認 — Timeoutのみで多重起動対策として十分と判断したのか、ReservedConcurrentExecutionsの追加要否について最終決定しているか、次回確認すること。

## 0008. contracts.contract_cd への UNIQUE 制約追加は行わない

- ステータス: 提案中（TODO: 要確認あり）
- 日付: 2026-10-02
- 対象システム・機能: UDS / `contracts` テーブル
- 決定者: a-nozawa

### コンテキスト

プレモータムレビューで、`contracts.contract_cd` にUNIQUE制約が無いことが、EventBridge多重起動時の重複INSERTを許してしまう一因であると指摘した。対策としてUNIQUE制約の追加を提案した。

### 検討した代替案

#### 案A: `contracts.contract_cd` にUNIQUE制約を追加する
- 内容: DBレベルで契約CDの一意性を保証する。
- メリット: アプリケーション側の「存在チェック→INSERT」のロジックに不具合があっても、DBレベルで重複を防げる。
- デメリット: 既存データに重複がある場合マイグレーションが失敗する可能性がある。制約追加の影響範囲の精査が必要。

#### 案B: 追加しない
- 内容: 現状のまま。
- メリット: 変更不要。
- デメリット: アプリケーション側のチェックのみに依存するため、0007の多重起動対策が不十分な場合は重複INSERTのリスクが残る。

### 決定

**案B（追加しない）を採用**。ただし、この判断の具体的な理由（既存データの重複有無、他テーブル設計上の制約、0007のTimeout対策で代替可能と判断したのか等）は会話内で明示されていない。

## 0009. CPM通知API・UX SQS送信をコミット確定後にまとめて実行する方式に変更する（0003・0005を置き換え）

- ステータス: 承認
- 日付: 2026-10-02
- 対象システム・機能: UDS / import_contract Lambda
- 決定者: a-nozawa

### コンテキスト

0003・0005では、CPM通知API・UX SQS送信がトランザクションのコミット前（work DELETE直前）に実行される設計を前提に、「ロールバック→再処理による重複呼び出しは運用上許容する」と決定していた。レビューの中で、`import_neos_uairplan`が採用している「全ラウンド処理完了後、コミット確定済みの行についてのみ外部連携をまとめて実行する」設計（`tmpStorage`方式）に合わせたいという方針が示され、重複呼び出しのリスクそのものを構造的に解消する方向に変更することとした。

なお、`改修概要書.md`（2026-09-11作成のドラフト）の変更後フロー図には、当初から「CPM 通知 API → UX SQS（commit後一括）」という同様の意図を示す記載が一部にあった。しかし実装時に参照された正式仕様書（Googleドキュメント「改修概要_import_contract への取込処理変更」）および実際の実装（GitLab MR #211）は、トランザクション内・コミット前に呼び出す設計になっていた。本決定は、当初ドラフトが意図していた設計に立ち返るものでもある。

### 検討した代替案

#### 案A: 現状維持（コミット前に都度実行、重複は許容）
- 内容: 0003・0005の決定を維持し、`pendingCpm`/`pendingUxData`をトランザクション内・work DELETE直前で呼び出す現行実装のままとする。
- メリット: 実装変更が不要。
- デメリット: ロールバック→次回バッチでの再処理のたびに、CPM通知・UX送信が重複する可能性が残る。

#### 案B: コミット確定後にまとめて実行する（import_neos_uairplan方式）
- 内容: 各行の処理では、コミット（DELETE+commit）成功時に外部連携情報（`pendingCpm`/`pendingUxData`）を配列（`pendingExternalCalls`）に退避するだけに留める。ラウンドロビンの全ラウンドが完了した後、配列の内容を1件ずつ順に実行する。1件の外部連携が失敗しても他の件の実行は継続し、失敗時はGoogle Chat通知を行う。
- メリット: 一度コミットされた行は二度とworkに戻らず再試行されないため、外部連携も構造的に一度きりになる。重複呼び出しのリスクを根本的に解消できる。
- デメリット: 外部連携自体が失敗した場合、該当行はDB上は正常に処理済み（workからも削除済み）なのに通知だけが届かない状態になる。workに残らないため自動再試行の対象にもならず、Google Chat通知による検知と手動対応に依存する。

### 決定

**案B（コミット確定後にまとめて実行）を採用**。0003（CPM重複許容）・0005（UX重複許容、contract_cdベースのキー変更は不採用）の決定を、本決定で置き換える（両ADRのステータスを「廃止（後継: 0009）」に変更）。

重複呼び出しを「許容する」のではなく構造的に防止する方が望ましいと判断した。新たに生じる「外部連携失敗時に自動再試行されない」というリスクについては、Google Chat通知による検知・手動対応で許容可能と判断した（この点はユーザー確認済み: 「問題なし」）。

なお、本ADR作成時点では、コードへの反映はMRへのレビューコメントとして提案するに留め、`import_contract/index.js`自体への直接の変更は行っていない（他の担当者が作業中のMRブランチであるため）。

### 影響・トレードオフ

- 性能・データ量急増時への影響: 外部連携をループ外でまとめて実行する形に変えても、1回のLambda実行内でのCPM/UX呼び出し件数自体は変わらないため、実行時間への影響は軽微と見込む。
- 他システムへの影響: CPM・UXへの重複通知が構造的に無くなる。一方、外部連携が失敗した行は手動対応が必要になり、運用負荷が「重複対応」から「通知漏れ対応」にシフトする。
- 運用・保守への影響: Google Chat通知の監視が、DB処理エラーだけでなく外部連携エラーの検知にも使われるようになる。
- 今後変更する場合の制約: 外部連携の失敗を自動リトライしたい場合は、別途リトライ用テーブル・キューの追加等、さらなる設計変更が必要になる。
