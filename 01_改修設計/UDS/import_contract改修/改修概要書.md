# 改修概要書：import_contract 取込アーキテクチャ変更（work テーブル経由の非同期処理）

作成日: 2026-09-11
対象システム: UDS (uds-web)

---

## 1. 改修背景・目的

### 背景

現行の `import_contract` Lambda は S3 PUT トリガーで起動し、TSV ファイルを1行ずつ同期処理する。処理時間は行数・外部API（CPM通知API / UX SQS）次第で変動し、Timeout 900秒に近づくリスクがある。同様の問題を抱えていた `import_neos_uairplan` では「work テーブル経由の非同期処理」（preprocess Lambda → work テーブル → import Lambda（EventBridge 10分））に移行して解決した。

### 課題

| 課題 | 内容 |
|-----|------|
| Timeout リスク | 行数が多い TSV を投入すると Lambda が 900秒に近づく |
| S3 トリガーの同期処理 | ファイル投入と同時に全行を処理するため、大量ファイル投入時に並列起動・競合が起きうる |
| トランザクション制御なし | 現行コードの `beginTransaction` / `commit` / `rollback` はコメントアウトされており、エラー時の部分コミットが残る |

### 目的

- work テーブルを挟んで非同期化することで、1 Lambda 実行あたりの処理件数を 1000件以下に制限し、Timeout リスクを排除する
- EventBridge 10分間隔のラウンドロビン処理で、同一 contract_cd の行が滞留しても他 contract_cd の処理をブロックしない
- トランザクション制御を復活させ、部分コミットを防止する

---

## 2. 改修対象一覧

| 対象 | 変更種別 | 主な変更内容 |
|------|---------|-------------|
| `preprocess-contract-tsv`（Lambda） | **新規** | S3 トリガー。SGSコピー・バリデーション・work テーブル INSERT を担う |
| `import_contract`（Lambda） | **改修** | S3 トリガー → EventBridge 10分トリガーに変更。work テーブルから1000件ずつ取得して処理 |
| `work_imported_contract`（DB テーブル） | **新規** | preprocess → import 間の受け渡しバッファ |

### 新規作成物

| 種別 | 名称 | 内容 |
|-----|------|------|
| Lambda | `preprocess-contract-tsv` | S3 PUT トリガー・TypeScript・Node.js 24.x・AWS SAM |
| DB テーブル | `work_imported_contract` | 53 TSV カラム + 管理カラム（UDS DB / `uds` スキーマ） |

## 3. 変更前後フロー比較

### 変更前

```
S3 PUT（{env}-udsapi-contract）
  → import_contract Lambda（S3 トリガー / Timeout 900秒）
      1. SGS バケットへコピー
      2. TSV を S3 から取得
      3. バリデーション（列数 / NULL 必須 / 文字数 / DateTime）
      4. 行ごとに:
         - device_types で neos_item_cd 存在チェック
         - isExistData で新規/既存分岐
         - contracts INSERT / UPDATE
         - shipping_requests INSERT / UPDATE
         - serials UPDATE / direct_shipments INSERT
         - BGM 処理
         - CPM 通知 API 呼び出し
         - UX SQS 送信
         - U90/U91/U92: UNIS DB 参照・更新
      5. done / error フォルダへコピー → 元ファイル削除
```

### 変更後

```
S3 PUT（{env}-udsapi-contract）
  → preprocess-contract-tsv Lambda（S3 トリガー / Timeout 300秒）
      1. SGS バケットへコピー（3リトライ）→ 失敗: error フォルダ + Google Chat通知 + 終了
      2. TSV をストリームで 1000行バッチ読み込み
      3. 列数チェック（53列）→ 不一致: Google Chat通知 + スキップ
      4. NULL 必須チェック → 不一致: Google Chat通知 + スキップ
      5. device_types の neos_item_cd バルクSELECT → 存在しない行はスキップ（ログ出力）
      6. 存在する行のみ work_imported_contract にバルク INSERT
      7. done / error フォルダへコピー → 元ファイル削除

EventBridge（10分ごと）
  → import_contract Lambda（Timeout 900秒）
      1. UDS MySQL + UNIS MySQL 接続
      2. work_imported_contract から 1000件取得
         （WHERE deleted_at IS NULL ORDER BY id ASC LIMIT 1000）
      3. 0件なら終了
      4. contract_cd でグループ化（id ASC 順維持）
      5. ラウンドロビン（各グループから 1行ずつ）:
         a. バリデーション（文字数 / DateTime）
            → エラー: Google Chat通知 + このグループの残り全行スキップ
         b. beginTransaction
         c. UNIS DB からエリア情報取得
         d. isExistData で新規/既存分岐
            - 新規: contracts INSERT → shipping_requests INSERT（センターCD決定ロジック）
                    → direct_shipments INSERT（対象CDのみ）→ BGM 処理
                    → CPM 通知API / UX SQS の送信要否を判定（呼び出しはまだ行わず退避）
            - 既存: contracts UPDATE → updateUdsStatus → BGM 処理
                    → UX SQS の送信要否を判定（呼び出しはまだ行わず退避）
         e. U90/U91/U92: UNIS DB 参照・更新
         f. commit（CPM/UX はまだ呼び出さない）
         g. work DELETE（id 指定）
         h. コミット成功した行のみ、退避していたCPM/UX呼び出し情報を pendingExternalCalls に積む
      6. 全ラウンド完了後、pendingExternalCalls を1件ずつ順に実行（CPM通知API → UX SQS）
         → 失敗時: Google Chat通知のみ（DBは既に確定済みのため work には戻らず、自動再試行されない）
```

※ 2026-10-02 のレビューで、CPM/UX呼び出しのタイミングを「コミット前」から「コミット確定後に一括実行」へ変更する方針に修正した（ADR 0009）。なお本ドラフト作成時点（2026-09-11）でも「commit後一括」という記載を一部に残していたが、実際にはMR #211で「コミット前」の設計が実装されていた。詳細は `ADR.md` 0009参照。

## 4. 期待効果

| 項目 | 変更前 | 変更後 |
|-----|-------|-------|
| 1回の Lambda 実行で処理する行数 | TSV 全行（無制限） | 最大 1000件 |
| 最悪ケースの処理時間 | 行数×処理時間（Timeout 超過リスクあり） | 1000件 × 500ms ≈ 500秒（Lambda 15分制限内） |
| 同時 Lambda 起動リスク | S3 PUT と同期 → 複数ファイル同時投入で並列起動 | EventBridge 1つ・`reserved_concurrency = 1` で直列化 |
| トランザクション制御 | なし（部分コミットの可能性） | 1行 1トランザクション |
| work テーブル滞留時の上限 | - | 10分 × 1000件。5000件超でアラーム推奨 |

## 5. 影響範囲・リスク

### 他システムへの影響

- **SGS**: SGS バケットへのファイルコピーは preprocess 側に移動するが、コピー先・ファイル名は変わらない
- **CPM / UX SQS**: 通知・送信は import 側に残るが、呼び出しをコミット確定後にまとめて実行する設計に変更し、ロールバック→再処理による重複呼び出しを構造的に防止する。代わりに、外部連携自体が失敗した場合はworkに残らず自動再試行されないため、Google Chat通知による検知・手動対応が必要（`ADR.md` 0009参照。0002/0003時点の「重複を許容する」という決定は0009で置き換え）
- **UX SQS**: FIFO キューのため Message Group ID による順序保証は維持される

### 移行・切り替え時の注意点

- preprocess デプロイ後、S3 イベント通知を旧 Lambda から新 Lambda に切り替える
- import 側の EventBridge スケジュールを設定してから、旧 S3 トリガーを削除する
- work テーブルが空の状態でリリースすること（旧 Lambda で処理中のファイルがない状態）

### リスク

| リスク | 内容 | 対策 |
|-------|------|------|
| タイムアウト | CPM API 遅延時に 1000件処理が 15分超 | CloudWatch で実行時間モニタリング。問題時は LIMIT を 500に引き下げ |
| 冪等性（DB INSERT） | contracts INSERT 後・work DELETE 前にクラッシュ → 次回リトライで isExistData=true を返し UPDATE ルートに入る | `contracts` の `contract_cd` UNIQUE 制約と `direct_shipments` の重複チェックで二重 INSERT を防止（既存コードで対応済み） |
| 滞留 | ピーク時に大量行が滞留すると解消が遅延 | work テーブルの未処理件数を CloudWatch カスタムメトリクスで監視 |
| 外部連携失敗時の通知漏れ | コミット確定後にCPM/UX送信が失敗すると、該当行はworkに残らず自動再試行されない | Google Chat通知で検知し手動対応する（`ADR.md` 0009） |
