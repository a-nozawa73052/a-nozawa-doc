# UDS PHP 8.5 移行 テスト計画書

作成日: 2026-10-22
対象システム: UDS（uds-web）
関連: [テストケース一覧.md](テストケース一覧.md) / [テストケース一覧.html](テストケース一覧.html)

---

## 1. 背景と目的

### 背景
- 2026/10/21 に、PHP 本体の Critical な脆弱性 **CVE-2026-109618 / CVE-2026-109619**（通称 php2shell。認証なしでリモートからコードを実行される）が公開された。
- AWS の告知（[2026-143-AWS](https://aws.amazon.com/jp/security/security-bulletins/2026-143-aws/)）では、**PHP 5.4〜8.1 は修正版が出ない**。UDS（uds-web）は **PHP 5.6** なので、これに当たる。
- 修正版が出るのは 8.2〜8.5 の系列。8.5 系は **8.5.12** が最初の修正版。
- 暫定対応として `session.upload_progress.enabled = Off` を入れている（UDS は外部からアクセスできない）。ただし、根本的に直すにはサポートされている PHP への移行が必要。

### 目的
- uds-web を **PHP 8.5.12 以上**に移行しても、業務機能が今と変わらず動くことを、手作業の回帰テストで確かめる。
- サーバーの作り直し（OS・Apache・PHP の設定、外部への接続）に漏れがないことを確かめる。
- 本番の切り替えと切り戻しの手順を、事前にリハーサルしておく。

## 2. 移行の内容（テストの前提）

PHP を上げると、フレームワークとライブラリも置き換えが必要になる。テストはこれらがすべて終わった状態に対して行う。バージョンは移行作業の中で決めるので、この表は**仮置き（要確認）**。

| 対象 | 今 | 移行後（仮） | 補足 |
|---|---|---|---|
| OS | Amazon Linux 2 + remi | Amazon Linux 2023 など | AL2023 で 8.5.12 以上のパッケージが入るかは要確認 |
| PHP | 5.6（mod_php5） | 8.5.12 以上（mod_php または php-fpm） | |
| FuelPHP | 1.7.2 | 1.8.2 以上（PHP 8 対応の系列） | 8.5 での動作実績は要確認。Crypt の方式が変わる |
| PHPExcel | 1.8.1 | PhpSpreadsheet | 使い方が変わる（列番号が 1 始まり、クラス名など） |
| TCPDF / FPDI | 6.2.12 / 1.6.1 | 6.7 以上 / 2.x | FPDI はクラス名が変わる |
| AWS SDK（手動で配置） | 3.276.0（Guzzle 6） | 最新の 3.x（Guzzle 7） | |
| Monolog | 1.5.0 | 1.27 以上または 2.x 以上 | |
| phpqrcode（手動で配置） | 1.1.4 | 続投または別のライブラリ | 8.x で非推奨の警告が出る可能性 |
| Smarty・php-markdown・Image_QRCode | 入っている | **削除** | どれもアプリから使われていない |

### 対象

- 5 章で「既存の不具合・既存の挙動」とした事象の修正。

## 4. テストの進め方

### 基本方針
- **旧環境（PHP 5.6）の挙動を正解**とする。同じデータで同じ操作をし、同じ結果になれば合格。
- 旧環境と新環境の stg を並べ、DB は**同じ時点のコピー**を使う。
- ファイル出力（CSV・Excel・PDF）は、両方の環境で出力して比べる。
  - CSV: WinMerge などでバイト単位で比べる（日時など、差が出て当然の項目は除く）。
  - Excel: セル単位で比べる。
  - PDF: 重ねて比べ、ラベルプリンタでも実際に印刷する。
- 画面の確認とあわせて、**毎日の終わりにエラーログを見る（CMN-01）**。UDS は PHP の非推奨の警告まで例外として扱い、画面を 404 などにしてしまうので、画面を見るだけでは気づけない不具合がある。

### 実施の順番
| フェーズ | 内容 | 対象のケース | 次に進む条件 |
|---|---|---|---|
| 0. 基盤の確認 | サーバーができた直後に、設定と接続を確かめる | INF | INF の「高」がすべて OK |
| 1. スモーク | 全ロールでログインし、主な画面が開くかを確かめる | AUT-01〜04、各区分の一覧画面 | 致命的な不具合がない |
| 2. 機能の回帰 | 優先度「高」→「中」→「低」の順で行う | CEN・JIM・BRA・EXT・CP・HOS・MST・UPL・DL・XLS・PDF・LNK・TSK | 「高」がすべて OK |
| 3. 横断・異常系 | 異常な入力、URL の直打ち、ロールバック | CMN・AUT の残り | 「高」がすべて OK |
| 4. 性能 | 旧環境と時間を比べる | PRF | 合意した基準以内 |
| 5. 切替のリハーサル | stg で切り替えと切り戻しを通しで行う | MIG-01・02 | 手順書が確定する |
| 6. 本番の切り替え | 切り替えた直後に確認する | MIG-03〜05 | すべて OK（NG ならすぐ切り戻す） |

## 5. 合格の基準

### 全ケース共通の合格条件
各ケースの期待結果に加えて、次の 3 つを満たすこと。
1. 画面が 404・403・500 などのエラー画面に変わらない（旧環境で同じ画面になる場合は除く）。
2. その操作の時間帯に、Fuel ログ・application.log・Apache の error_log へ **PhpErrorException・Deprecated・Warning・Fatal が出ていない**。
3. DB の更新内容（件数・値・updated_at）が旧環境と同じ。

### 全体の合格基準
| 優先度 | 基準 |
|---|---|
| 高 | 全件を実施し、**全件 OK** |
| 中 | 全件を実施する。NG が残るなら、回避策と修正時期について業務担当と合意している |
| 低 | 実施する。時間がない場合は、やらないことを合意して記録する |
| 共通 | NG・保留の不具合がすべて、修正済みか合意のうえで持ち越しになっている |

## 6. 重点的に見るリスク

ソースを調べて分かった、PHP 8 で壊れやすい箇所。テストケースの「PHP 8 のリスク・根拠」の欄と対応している。

| # | リスク | 起きること | 関係するケース |
|---|---|---|---|
| R1 | Fuel が E_DEPRECATED・E_WARNING も例外にする（`error_reporting(-1)`）。PHP 8 では `@` で抑えた警告も例外になる | null を文字列関数に渡すなど、PHP 8.1 以降で増えた非推奨の警告ひとつで、画面が 404 やエラーになる | CMN-01 ほか全体 |
| R2 | PHPExcel・TCPDF 6.2・FPDI 1.6 が PHP 8 で動かない（構文エラー・`each()`） | Excel・PDF の出力がすべて止まる。置き換えると列の位置やレイアウトがずれるおそれ | XLS・PDF・CEN（出荷）・JIM |
| R3 | Fuel を 1.8 にすると Crypt の方式が変わる | 旧環境で発行した Cookie を復号できず、全員が一度ログアウトされる。セッションのエラー | AUT-07 |
| R4 | `count()` に null や文字列が渡る | チェックを付けずに確定すると TypeError | CMN-03・05 |
| R5 | null のオブジェクトへのプロパティ代入 | 存在しない ID・出荷依頼のない端末を操作すると Error | CMN-02・CEN の回収 |
| R6 | `catch(\Exception)` では `\Error` / TypeError を捕まえられない | トランザクションの途中で落ちてもロールバックされず、データが半端になる | CMN-12・UPL のロールバック |
| R7 | SJIS の変換（SJIS-win と cp932 が混在、mbstring の変更）、`fputcsv` の escape 引数の省略（8.4 以降は非推奨） | 機種依存文字が化ける、CSV の列がずれる、出力時に例外 | UPL の共通・DL の共通 |
| R8 | PHP 8.1 以降の PDO は INT 列を int で返す | `!==` の差分判定が変わり、変更がないのに updated_at が更新される | CMN-10 |
| R9 | `.htaccess` の `mod_php5` の分岐から外れる | ルーティングやクエリ文字列の扱いが変わる | INF-11 |
| R10 | サーバーを作り直したことによる設定漏れ | FUEL_ENV が未設定で test 環境になる、書き込み権限、IAM、送信元 IP、緩和策の設定漏れ | INF |
| R11 | AWS SDK と Guzzle の更新 | S3・SQS・署名 URL の動きが変わる | LNK |

## 7. テスト環境とデータ

### 環境
| 環境 | 用途 | 備考 |
|---|---|---|
| 旧 stg（PHP 5.6） | 正解の結果を出す | 今の stg をそのまま使う |
| 新 stg（PHP 8.5） | テストする | 本番と同じ手順で作る |
| DB | 両方の環境に同じ時点のコピーを用意する | テストの途中でデータがずれたら、もう一度コピーする |
| S3 | 環境ごとにバケットを分けるか、プレフィックスで分ける | export_lists と同じ |
| 外部 API（U-NEXT・Arteria） | stg の接続先を使う | 本番 API は呼ばない |

### 用意するテストデータ
- 全 7 ロールのテストユーザー（管轄違いを含む）。
- 端末ステータス・依頼種別（通常新設 1・デジ化 3・緊急 4・交換 5 など）ごとの代表データ。
- 東センター・西センターそれぞれの管轄の依頼。
- CSV（SJIS）: 正常データ、機種依存文字（①㈱髙～－・「ソ」「表」）、形式エラー、入力エラー、途中の行だけエラー、19MB 程度・20MB 超、UTF-8（BOM あり・なし）。
- 大量件数のデータ（SIM 一覧・端末リストで本番相当の件数）。

## 9. 不具合の管理

- NG になったら、テストケース一覧の「結果」を NG にし、Backlog の課題番号をメモする。
- 課題には、ケース ID・再現手順・旧環境での結果・新環境での結果・エラーログを書く。
- 修正したら、そのケースと、同じ部品を使う関連ケースをもう一度テストする（例: PDF の基底クラスを直したら PDF のケースをすべて）。

## 10. 判断が必要な事項

### 10-1. 既存の不具合・既存の挙動の扱い
調査の中で、**今の環境でもすでに起きている**と思われる事象が見つかった。このテストでは「旧環境と同じなら合格」として扱い、直すかどうかは別に判断する。

| 事象 | 場所 | 案 |
|---|---|---|
| CP 検証機管理の画面（cp/mirroring の 4 本）が、**ログインしていなくても開ける** | `controller/cp/mirroring/*.php`（Controller_Hybrid を直接継承） | 外部からアクセスできない前提で今回は維持し、別途直す |
| UME(TV) の引き当てで、UX 開局の SQS 送信が redirect の後にあり、実行されない | `controller/center/assign.php` | 業務に影響があるか確認する |
| `/manage/request` がどのロールでも 403 になる（使われていない画面） | `controller/request.php` | 削除を検討する |
| 紛失報告の `keep_flash` にキーが文字列のまま渡されている | `controller/center/device/lost.php` | 影響が小さいので維持 |
| 修理交換で、配列を ID に代入している | `controller/center/device/list.php` | 業務に影響があるか確認する |

### 10-2. 今回の範囲外で見つかったセキュリティ上の指摘（報告のみ）
| 指摘 | 場所 |
|---|---|
| ユーザーのパスワードを平文で保存・比較している | `classes/auth/login/mosauth.php`（`hash_password()` が入力値をそのまま返す） |
| API キーなどを含む `.env` を Web 公開ディレクトリ（`public/.env`）に置く作り | `classes/common/env.php` |
| 別案件から流用したバックアップスクリプトに、DB パスワードが平文で書かれている | `backup_script/` |

### 10-3. 未決事項
- 移行後の OS と、ライブラリのバージョン（2 章）。
- PHP の実行方式（mod_php か php-fpm か）。
- 性能の合格基準（仮: 旧環境の 1.2 倍以内）。
- 旧サーバーを残しておく期間と、切り戻しの判断基準。
- 本番の php.ini・Apache の設定がリポジトリにないので、旧本番サーバーから取り出して新サーバーと比べる。
