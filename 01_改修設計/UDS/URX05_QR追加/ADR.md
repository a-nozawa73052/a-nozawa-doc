## 0001. CSVマスタアップロードの qrcode_flg バリデーション改修を本改修のスコープに含める

- ステータス: 承認
- 日付: 2026-09-03
- 対象システム・機能: UDS（uds-web） / キッティング画面 QRシール印刷機能
- 決定者: TODO: 要確認（本チャットでの合意者名を記載）

### コンテキスト

URX対応では `device_types.qrcode_flg = 2` という新しい値を扱う。改修概要書の当初案では「`qrcode_flg = 2` のマスタデータ投入は本改修のスコープ外。別途データ投入を依頼する」としていた。

しかしレビューの過程で、CSVマスタアップロードのバリデーション処理 `classes/upload/csv/master/device.php` の `validate_qrcode_flg()` が `'0'`・`'1'` 以外の値を常にエラーとする実装になっていることが判明した。このため、`qrcode_flg = 2` のレコードを一度DBに投入したとしても、以後そのレコードを通常のCSVマスタアップロード画面から更新しようとすると、値が変わっていなくてもバリデーションエラーで弾かれ続ける。「マスタデータの初回投入」と「バリデーションロジックの改修」は別問題であり、後者を放置すると恒久的にURX機種のマスタ更新が通常フローで行えなくなる。

### 検討した代替案

#### 案A: validate_qrcode_flg() 改修を本改修のスコープに含める
- 内容: `'0'`・`'1'`・`'2'` を許容するようバリデーションを修正し、エラーメッセージも「0、1、または、2で入力してください」に更新する
- メリット: URX機種のマスタ情報（型番名等）を将来にわたり通常のCSV画面から更新できる
- デメリット: 改修範囲・テスト範囲が広がる。バリデーション改修のリリースタイミングと `qrcode_flg = 2` の初回データ投入のタイミングの前後関係を管理する必要が生じる

#### 案B: スコープ外のまま据え置く
- 内容: 「初回データ投入」だけでなく「以後の更新」も含めて、`qrcode_flg = 2` のレコードは常にDB直接操作で対応する運用ルールとして明記するに留める
- メリット: 今回の改修範囲を最小化できる
- デメリット: 恒久的な運用上の制約（CSV画面が使えない機種が存在し続ける）を許容することになり、将来的な保守コストが増える

### 決定

案Aを採用。マスタ更新が通常フローで完結しない状態を恒久化するのは保守性の観点で望ましくないと判断した。ただし初回データ投入自体（`qrcode_flg = 2` を持つレコードをいつ・誰が投入するか）は引き続きスコープ外とし、バリデーション改修のリリースとデータ投入の前後関係を確認事項として改修概要書8章に残した。

### 影響・トレードオフ

- 性能・データ量急増時への影響: なし（バリデーションロジックの分岐追加のみ）
- 他システムへの影響: なし（UDS内のCSVマスタアップロード機能に閉じる）
- 運用・保守への影響: バリデーション改修のリリースが `qrcode_flg = 2` の初回データ投入より後になった場合、投入時点では通常のCSV画面から投入できず、代替手段（DB直接投入等）が必要になる。リリース順序の調整が運用上の前提条件となる
- 今後変更する場合の制約: 特になし

## 0002. 同一依頼IDへの同時実行対策は「一時ファイル名のトークン化」のみとし、DB排他制御による二重実行防止は行わない

- ステータス: 承認
- 日付: 2026-09-03
- 対象システム・機能: UDS（uds-web） / キッティング画面 QRシール印刷機能（複数ページPDF生成）
- 決定者: TODO: 要確認（本チャットでの合意者名を記載）

### コンテキスト

`premortem-reviewer` サブエージェントによるプレモータムレビューで、以下のリスクが指摘された。

セット品対応により、QR印刷アクションは対象行ごとに一時QR画像（`{shipping_request_id}_{row_id}.png`）を生成してPDF化する。この命名規則は「異なるセット間の衝突」は防げるが、「同一依頼IDに対する処理が同時に2回実行される」ケース（ダブルクリック・複数タブ・複数端末からの同時押下等）には無力である。ファイル名が依頼IDと行IDから決定的に導出されるため、同一依頼IDへの同時実行では2つの処理が同一ファイルパスへ競合して書き込み、誤ったQR画像が別ページに混入する恐れがある。クライアント側の `data-lock` はDOM要素単位のロックであり、別タブ・別端末からの同時実行は防げない。

既存の `shipping_requests.lock_date` / `lock_user_id` カラムは `controller/center/assign.php` および `presenter/center/request/index.php` で「画面編集ロック」（他ユーザーによる編集中表示、10分間の楽観ロック）として既に使われている。QR印刷の排他制御にこれを流用すると、QR印刷時にこのロック情報を書き換えてしまい、無関係な依頼一覧画面（`presenter/center/request/index.php`）でその依頼が誤って「他ユーザーが編集中」と表示される等、既存機能への副作用が生じる。

### 検討した代替案

#### 案A: 一時ファイル名のトークン化のみ
- 内容: 一時QR画像のファイル名に、行の一意性（`row_id`）に加えてリクエスト実行ごとに一意なトークン（`uniqid()` 等）を付与する（例: `{shipping_request_id}_{row_id}_{token}.png`）
- メリット: 実装コストが低い。既存のロックカラムや他画面のロジックに一切触れないため、副作用のリスクがない。同時実行が起きても、双方の処理がそれぞれ独立したファイルに書き込むため、ファイル破損・誤ったQRの混入は確実に防げる
- デメリット: 同時実行そのものは防止しない。同一依頼IDへの二重押下が起きた場合、無駄な二重処理（QR生成・PDF生成が2回走る）や、二重のPDFダウンロードが発生し得る

#### 案B: トークン化 + DB Advisory Lock（`GET_LOCK()`）による二重実行防止
- 内容: 案Aのトークン化に加え、QR印刷アクションの入口で依頼IDをキーにしたMySQLのAdvisory Lock（`GET_LOCK()`）を取得し、既にロックされている場合は「印刷中です」等のエラーを返して後発の処理を弾く
- メリット: ファイル破損防止に加え、二重処理・二重ダウンロード自体も防止できる
- デメリット: ロック取得・解放（例外時の確実な解放を含む）を新規に実装・テストする必要があり、実装コストとレビューコストが増える。ロックの解放漏れが新たな障害要因になり得る

### 決定

案Aを採用。ファイル破損・QR誤混入という「物理的に誤ったシールが出荷される」重大リスクはトークン化で確実に防げる一方、二重処理・二重ダウンロードは「無駄な処理が起きるが実害はない」レベルのリスクであり、実装コスト・新規バグ混入リスクとのバランスから今回は許容することとした。現場運用上この二重処理が許容できるかは、改修概要書8章の確認事項として別途確認する。

### 影響・トレードオフ

- 性能・データ量急増時への影響: 同時押下が発生した場合、QR生成・PDF生成処理が二重に走るため、その間だけサーバー負荷が一時的に倍増する。ただし恒常的な負荷増ではない
- 他システムへの影響: なし（既存の `lock_date`/`lock_user_id` を使う画面には触れない）
- 運用・保守への影響: 同一依頼IDへの同時押下時に二重にPDFがダウンロードされる可能性があることを、現場運用側に周知する必要がある
- 今後変更する場合の制約: 将来的に二重処理自体を防ぎたくなった場合は、案Bまたはそれに準ずる排他制御を別途追加で検討する

### 関連

## 0003. shipping_requests.id 昇順ソートは共通ヘルパーを変更せず、QR印刷アクション内でのみ実施する

- ステータス: 承認
- 日付: 2026-09-03
- 対象システム・機能: UDS（uds-web） / キッティング画面 QRシール印刷機能（複数ページPDF生成）
- 決定者: TODO: 要確認（本チャットでの合意者名を記載）

### コンテキスト

複数ページPDF生成では、各ページを `shipping_requests.id` 昇順で並べる必要がある。しかし、対象行の取得に使う `Controller_Center_Kitting::get_set_shipping_request()` はセンター向けキッティング機能内の複数アクション（`action_select_list`、`action_view`、`action_return` 等）から共有されている既存の非公開ヘルパーで、デフォルトの並び順は `device_types.device_type` 昇順→`created_at` 降順であり、`id` 昇順ではない。

プレモータムレビューで、「id昇順ソートを行う」という要件を実装者が `get_set_shipping_request()` の並び順を暗黙のうちに信頼して見落とす、あるいは共通ヘルパー自体の並び順を変更してしまい他アクションに影響する、という2方向のリスクが指摘された。

### 検討した代替案

#### 案A: QR印刷アクション内でのみ `usort()` 等により再ソートする
- 内容: `get_set_shipping_request()` はそのまま呼び出し、返却された `$rows` をQR印刷アクション（`action_download_qrcode_label_save` / `action_download_urx_qrcode_label_save`）の中でのみ `id` 昇順に再ソートする
- メリット: 共通ヘルパーのシグネチャ・挙動を一切変更しないため、他の呼び出し元（select_list/view/return等）への影響範囲確認が不要
- デメリット: 実装者が明示的に再ソート処理を書き忘れるとバグになる（ドキュメント・レビューでの明記が必須）

#### 案B: `get_set_shipping_request()` にソート切替引数を追加する
- 内容: 例えば `$order_by_id = false` のような引数を追加し、QR印刷アクションからの呼び出し時のみ `true` を渡してid昇順にする
- メリット: ソート処理が共通ヘルパー内に閉じ、QR印刷アクション側のコードがシンプルになる
- デメリット: 共通ヘルパーのシグネチャ変更になるため、他の呼び出し元すべてに影響がないことを確認する必要があり、影響範囲確認のコストが増える

### 決定

案Aを採用。影響範囲を今回の改修対象（QR印刷アクション）のみに限定するため。実装時・レビュー時に再ソート処理の実装漏れがないことを確認することを、改修概要書3-3節に明記した。

### 影響・トレードオフ

- 性能・データ量急増時への影響: なし（ソート対象はセット内の行数のみで、通常数件〜十数件程度）
- 他システムへの影響: なし
- 運用・保守への影響: 将来 `get_set_shipping_request()` の呼び出し元が増えた場合も、id昇順ソートの要否を呼び出し元ごとに個別に判断する必要がある
- 今後変更する場合の制約: QR印刷以外の機能でもid昇順ソートが必要になった場合、重複実装を避けるため案B（共通ヘルパー側への切替引数追加）を再検討してもよい

## 0004. プレモータムレビューで指摘されたシナリオ2・4・5（判定ロジックの二重実装、セット件数上限、CSVリリース順序）は今回は対応しない

- ステータス: 承認
- 日付: 2026-09-03
- 対象システム・機能: UDS（uds-web） / キッティング画面 QRシール印刷機能
- 決定者: TODO: 要確認（本チャットでの合意者名を記載）

### コンテキスト

`premortem-reviewer` によるプレモータムレビューで、シナリオ1・3（同時実行時のファイル衝突、id昇順ソートの実装漏れ）に加え、以下3件のリスクシナリオが指摘された。

- シナリオ2: ボタン表示判定（`ume_flg`/`urx_flg`）と実際の印刷対象行判定（`get_ume_eligible_rows`/`get_urx_eligible_rows`）が別ロジックのため、実装時の些細な差異でボタン表示と実際の印刷結果が乖離する可能性がある（エラーが出ないため気付きにくい）
- シナリオ4: 1セットあたりの依頼件数に上限がなく、想定外の大量データが1セットに紐づいた場合、QR画像生成・PDF生成のループ処理でタイムアウト・メモリ超過が発生し、一時ファイルが残留し続ける可能性がある
- シナリオ5: `qrcode_flg = 2` のマスタ投入と `validate_qrcode_flg()` 改修（0001参照）のリリース順序が逆転した場合、一時的にCSVマスタ更新がブロックされる（影響は限定的）

### 検討した代替案

#### 案A: 今回の改修スコープに含めて対応する
- 内容: シナリオ2はボタン表示判定と印刷対象行判定を同一ロジックから導出するよう設計変更、シナリオ4はセット件数上限のバリデーション追加、シナリオ5はリリース手順書への明記等
- メリット: 既知のリスクを未然に潰せる
- デメリット: 改修範囲・設計変更・テスト範囲がさらに広がり、リリース時期に影響する

#### 案B: 今回は対応せず、既知のリスクとして記録するに留める
- 内容: 上記3シナリオへの対応は行わず、ADRとして経緯を残す
- メリット: 改修スコープを、優先度の高いシナリオ1・3の対応にとどめられる
- デメリット: 指摘されたリスクが本番環境に残存する

### 決定

案Bを採用。理由の詳細（工数上の制約か、リスクの発生確率・影響度が相対的に低いと判断したか等）は本チャットの会話からは明確に読み取れないため、TODO: 要確認。

### 影響・トレードオフ

- 性能・データ量急増時への影響: シナリオ4（セット件数上限なし）のリスクが残存する。想定外の大量データが1セットに紐づいた場合の挙動は未検証のまま
- 他システムへの影響: シナリオ2（判定ロジックの乖離）のリスクが残存する。エラーが出ないため、発生時の検知が困難
- 運用・保守への影響: シナリオ5（CSVリリース順序）のリスクが残存するが、影響範囲は限定的（該当行のみブロック、DB直接更新で回避可能）
- 今後変更する場合の制約: 特になし。将来的にこれらのシナリオが顕在化した場合は、改めて設計を見直す

## 0005. ADR 0002で合意した一時ファイル名のトークン化対応を、本改修では見送る

- ステータス: 承認
- 日付: 2026-09-09
- 対象システム・機能: UDS（uds-web） / キッティング画面 QRシール印刷機能
- 決定者: TODO: 要確認

### コンテキスト

ADR 0002で、同一依頼IDへの同時実行時のファイル衝突対策として、一時QR画像ファイル名に
実行ごとの一意なトークンを付与する方針（案A）を承認した。しかし実際のPR（uds-web #302）の
実装ではこのトークン付与は行われず、`{行ID}.png`のみのファイル名のままとなっている。

### 検討した代替案

#### 案A: 予定通りトークン化を実装してからマージする
- 内容: PRにトークン化の追加実装を要求し、修正完了を待ってからマージする
- メリット: ADR 0002で識別したファイル衝突リスクを技術的に解消できる
- デメリット: 追加の実装・レビュー・再テスト工数が発生し、リリーススケジュールが遅延する

#### 案B: 今回のリリースではトークン化を見送り、現状のまま出荷する
- 内容: `{行ID}.png`のみの命名のままとし、トークン付与は次回以降の改修に持ち越す
- メリット: スケジュール遅延を回避できる
- デメリット: ADR 0002で識別した「同一依頼IDへの同時実行時のファイル衝突・QR誤混入」リスクが
  未対策のまま残る

### 決定

案Bを採用。スケジュールの都合を優先した。現状の運用では、同一依頼IDに対して複数タブ・
複数端末から同時に処理を行うケースが実態として起こりにくく、当面は運用上破綻しないと判断した。

### 影響・トレードオフ

- 性能・データ量急増時への影響: なし
- 他システムへの影響: なし
- 運用・保守への影響: 同一依頼IDへの同時実行が万一発生した場合、ADR 0002で指摘した
  「誤ったQRコードが物理シールとして印刷される」リスクが残る
- 今後変更する場合の制約: 次回以降の改修でトークン化（またはそれに準ずる排他制御）を
  追加実装する場合は、ADR 0002の案A・案Bを再度参照すること
